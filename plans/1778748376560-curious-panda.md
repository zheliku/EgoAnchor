# EgoAnchor NATS + Protobuf 通信与 Anchor 控制迁移计划

## 目标

将当前以 ZMQ + MessagePack 为主的 Quest 图像输入、Python pose tracking、Unity anchor 应用链路，逐步演进为可扩展的 NATS + Protobuf 架构。旧链路保持可运行，新链路并行开发、验证、替换，直到功能覆盖后再删除旧代码。

核心新增能力：

- Unity 侧提供 anchor API，替代 Python 本地键盘 `r` 触发 reset/re-register 的交互方式。
- 服务器端支持多类型消息、命令路由、请求-响应、发布-订阅、状态事件、错误返回、幂等命令与超时处理。
- 避免 Python server/pipeline 中继续堆叠 `if topic == ...` 和 `if command == ...`。
- 保留当前 frame_id 对齐、per-topic latest-drain、camera_info 标定、pose 回传与 Unity world anchor 应用的系统语义。

## 当前状态理解

当前主链路：

- Unity `PayloadSender` 用 ZMQ PUB multipart `[topic_utf8, payload_msgpack]` 发送 `quest_stereo` 与 `quest_camera_info`。
- Python `QuestReceiver` 用 ZMQ SUB 接收多 topic，并按 topic 保存最新消息。
- Python `object_tracking_server.py` 主循环调用 `QuestObjectTrackingPipeline.run()`，输出 `PoseMsg`，再用 ZMQ PUB 发送 `pose`。
- Unity `PayloadReceiver` 后台线程接收 pose，主线程按 topic 调用 `PoseDecoder`。
- Unity `FrameAlignedObjectAnchor` 通过 `frame_id` 回查发送该帧时的左目 camera pose，将 camera-local object pose 映射到 Unity world anchor pose。

当前 reset 语义：

- Python 本地键盘 `r` 通过 `handle_debug_key()` 调用 `pipeline.reset_tracking_state()`。
- `reset_tracking_state()` 会清空 `_has_pose`、Cutie、FoundationPose、last pose、mask snapshot，并用 `_reset_after_frame_id` 避免异步旧结果污染重注册。
- 该行为本身已经是一个清晰的领域命令，适合迁移为 Unity 发起的 `ResetTracking` / `RerunPoseEstimation` 命令。

当前不足：

- ZMQ topic 字符串和 MessagePack 字段约定依赖人工同步，类型安全弱。
- 只有 PUB/SUB，没有原生请求-响应、Ack、服务发现、请求超时语义。
- Python 输入接收和 pipeline 运行耦合较紧，命令处理需要新入口，否则会继续把逻辑塞进 server 主循环。
- 缺少通用 router/handler/command bus/state machine，后续 `reset`、`stage`、`hold`、`reacquire`、`health`、`config` 会导致 if-else 膨胀。
- 当前 NATS 试验代码已经验证 Unity/Python 基础连通，但仍是 JSON 字符串和单用途 demo，尚未形成协议、路由、状态和错误模型。

## 通信方案比较

| 方案 | 优点 | 缺点 | 适配结论 |
| --- | --- | --- | --- |
| ZMQ + MessagePack | 低延迟、无 broker、实现简单、当前已跑通；MessagePack 性能好，二进制字段方便传 JPEG | 无内建 schema/codegen；请求-响应、重试、命令 Ack、服务发现、可观测性都要手写；topic/字段靠约定；消息变多后管理成本上升 | 可继续作为旧链路和性能基线，但不适合作为长期控制面与多消息框架 |
| NATS + Protobuf | subject 天然路由；同时支持 pub/sub 与 request/reply；Python/C# 客户端成熟；Protobuf 强 schema、跨语言、性能好；NATS CLI/监控利于调试；后续可加 JetStream | 需要 NATS server 进程；需要 proto/codegen 管理；Unity async 和主线程派发要设计好；Protobuf 对动态调试不如 JSON 直观 | 推荐作为下一代主架构。Core NATS 用于实时流和命令，JetStream 暂不进首版 |
| gRPC + Protobuf | 类型安全强；请求-响应和 streaming 模型清晰；工具生态成熟 | Unity/Quest/IL2CPP/Android 集成和双向流维护成本更高；pub/sub fanout 和 latest-drain 需要额外层；不如 NATS 适合事件总线 | 不推荐作为主链路，可作为未来管理 API 的备选 |
| MQTT + Protobuf/JSON | broker、topic、QoS、保留消息成熟；IoT 场景常见 | 请求-响应不自然；高频低延迟图像流和复杂服务编排不如 NATS；Unity/C# 可用但事件语义较弱 | 不推荐，除非未来要接入 IoT 平台 |
| ROS2/DDS | typed pub/sub、QoS、工具链强，机器人领域成熟 | 体系重；Unity/Quest 集成复杂；部署和调试成本高；对本项目单 Python 服务 + Unity 客户端过度 | 不推荐当前阶段使用 |
| WebSocket + JSON/Protobuf | 易调试、部署简单、浏览器友好 | 无内建多 subject 路由、队列组、request/reply 语义；并发和协议管理仍需自建 | 适合作为 debug UI，不适合作主系统总线 |

明确推荐：

- 采用 NATS Core + Protobuf 作为新主线。
- 先不用 JetStream 承载实时 stereo/pose，因为这类消息追求 latest-only 和低延迟，不追求持久化。
- JetStream 只作为未来可选能力，用于实验日志、命令审计、离线回放、关键配置变更事件，而不是首版实时链路。
- 长期目标是全量迁移到 NATS + Protobuf，包括高频 stereo、camera_info、pose、state、command、health；旧 ZMQ + MessagePack 只在迁移期间保留，并作为端到端可运行回退路径。

## 架构原则

- 传输层不理解业务，只负责连接、发布、订阅、请求、响应、重连、关闭。
- Protobuf 是唯一跨语言消息契约；不再用手写 JSON 契约替代强类型消息。
- NATS subject 是第一层路由，Protobuf message type / oneof 是第二层领域路由。
- 高频流使用 pub/sub + latest-only buffer；命令使用 request/reply；状态变化使用 pub/sub event。
- pipeline 本身保持单线程/串行访问，避免 FoundationPose、Cutie、GPU 模型被并发调用。
- NATS callback 只做轻量解码、缓存、入队，不直接跑重模型。
- reset/reacquire 等命令通过 command queue 串行进入 pipeline runtime，避免和当前帧处理抢状态。
- 每个命令有 `command_id` / `correlation_id`，服务端按 TTL 去重，支持客户端安全重试。
- 长耗时动作先返回 accepted，再通过 `AnchorStateEvent` / `CommandProgressEvent` 广播执行结果。

## NATS 使用方式

Subject 命名建议：

```text
egoanchor.v1.quest.stereo              Unity -> Python, pub/sub, high frequency
egoanchor.v1.quest.camera_info         Unity -> Python, pub/sub, low frequency
egoanchor.v1.anchor.pose               Python -> Unity, pub/sub, latest pose/status
egoanchor.v1.anchor.state              Python -> Unity, pub/sub, state transitions
egoanchor.v1.anchor.events             Python -> Unity, pub/sub, domain events
egoanchor.v1.anchor.commands           Unity -> Python, request/reply command service
egoanchor.v1.server.health             Unity/debug -> Python, request/reply health
egoanchor.v1.debug.*                   optional debug subjects
```

首版不建议把 command 拆成大量独立 subject，例如 `...reset`、`...set_stage`、`...hold`。推荐先用统一 `egoanchor.v1.anchor.commands` request/reply，payload 是 `AnchorCommandRequest`，内部 `oneof command` 做二级路由。这样 Unity API 更稳定，Python command router 更集中。

对于高频 stereo/pose：

- 使用 Core NATS pub/sub。
- subscriber 侧实现 latest-only buffer，覆盖旧帧，不排队跑旧图。
- 不对每帧做 request/reply，不做重试。
- 记录 `frame_id`、`sender_mono_ms`、`unity_frame`、`message_id`，保留当前延迟估计能力。

对于命令：

- 使用 request/reply。
- Unity 设置超时，例如 reset 1-2 秒，rerun/reacquire 3-5 秒。
- 如果超时重试，必须复用同一个 `command_id`，服务端用幂等缓存返回相同或兼容结果。
- 命令执行成功或状态改变后，服务端额外发布 state/event，便于多个 Unity 组件或 debug 客户端同步状态。

对于状态和事件：

- `AnchorStateEvent` 广播 pipeline 状态，例如 `WAITING_CALIB`、`DETECTING`、`TRACKING`、`RESETTING`、`REACQUIRING`、`ERROR`。
- `AnchorEvent` 广播领域事件，例如 `RESET_APPLIED`、`REGISTER_STARTED`、`REGISTER_SUCCEEDED`、`TRACK_LOST`、`RE_REGISTER_SUCCEEDED`。
- Unity 不应只依赖 request reply 更新 UI，应同时订阅 state/events。

## Protobuf 消息设计

基本设计原则：

- 高频数据不要包 `google.protobuf.Any`，避免额外动态类型开销和调试复杂度。
- 每个 NATS subject 绑定一个明确 protobuf message。
- 命令 subject 可以使用 `oneof`，因为命令天然共享 Ack、幂等、错误和权限语义。
- 所有消息带 `Header`，但 header 保持小而稳定。

建议 proto 草案：

```proto
syntax = "proto3";

package egoanchor.v1;

message Header {
  string schema_version = 1;
  string message_id = 2;
  string correlation_id = 3;
  string session_id = 4;
  string source = 5;
  string anchor_id = 6;
  int64 frame_id = 7;
  double sender_mono_ms = 8;
  double sent_unix_ms = 9;
}

enum StatusCode {
  STATUS_CODE_UNSPECIFIED = 0;
  OK = 1;
  ACCEPTED = 2;
  INVALID_ARGUMENT = 3;
  NOT_READY = 4;
  CONFLICT = 5;
  TIMEOUT = 6;
  INTERNAL = 7;
}

message Status {
  StatusCode code = 1;
  string message = 2;
  string detail = 3;
}

message QuestStereoFrame {
  Header header = 1;
  bytes left_image_jpeg = 2;
  bytes right_image_jpeg = 3;
  int32 unity_frame = 4;
  int32 left_width = 5;
  int32 left_height = 6;
  int32 right_width = 7;
  int32 right_height = 8;
}

message QuestCameraInfo {
  Header header = 1;
  bool is_supported = 2;
  float left_fx = 3;
  float left_fy = 4;
  float left_cx = 5;
  float left_cy = 6;
  float right_fx = 7;
  float right_fy = 8;
  float right_cx = 9;
  float right_cy = 10;
  repeated float left_distortion = 11;
  repeated float right_distortion = 12;
  float baseline_m = 13;
  int32 sensor_width = 14;
  int32 sensor_height = 15;
  int32 active_left = 16;
  int32 active_top = 17;
  int32 active_right = 18;
  int32 active_bottom = 19;
  int32 left_requested_width = 20;
  int32 left_requested_height = 21;
  int32 right_requested_width = 22;
  int32 right_requested_height = 23;
  int32 current_width = 24;
  int32 current_height = 25;
  int32 max_framerate = 26;
  Pose3 left_lens_offset = 27;
  Pose3 right_lens_offset = 28;
}

message Vec3 { float x = 1; float y = 2; float z = 3; }
message Quat { float x = 1; float y = 2; float z = 3; float w = 4; }
message Pose3 { Vec3 position = 1; Quat rotation = 2; }

message PoseObservation {
  Header header = 1;
  string phase = 2;
  int32 stage = 3;
  int32 det_count = 4;
  float depth_valid_ratio = 5;
  float fps = 6;
  bool has_pose = 7;
  repeated float pose_matrix_row_major = 8;
  Timing timing = 9;
  Status status = 10;
}

message Timing {
  float segmentation_ms = 1;
  float depth_ms = 2;
  float cutie_ms = 3;
  float pose_ms = 4;
}

message ResetTrackingCommand {
  bool reset_anchor_processors = 1;
  bool force_next_frame = 2;
}

message RerunPoseEstimationCommand {
  bool clear_tracking_state = 1;
  bool wait_until_registered = 2;
  int32 max_wait_frames = 3;
  double timeout_ms = 4;
}

message SetStageCommand { int32 stage = 1; }

message AnchorControlCommand {
  enum Mode {
    MODE_UNSPECIFIED = 0;
    UPDATE = 1;
    SMOOTH = 2;
    HOLD = 3;
    REACQUIRE = 4;
  }
  Mode mode = 1;
}

message AnchorCommandRequest {
  Header header = 1;
  string command_id = 2;
  oneof command {
    ResetTrackingCommand reset_tracking = 10;
    RerunPoseEstimationCommand rerun_pose_estimation = 11;
    SetStageCommand set_stage = 12;
    AnchorControlCommand anchor_control = 13;
  }
}

message AnchorCommandReply {
  Header header = 1;
  string command_id = 2;
  Status status = 3;
  bool accepted = 4;
  bool applied = 5;
  string state = 6;
}

message AnchorStateEvent {
  Header header = 1;
  string state = 2;
  string phase = 3;
  Status status = 4;
  int64 generation = 5;
}

message HealthRequest { Header header = 1; }
message HealthReply {
  Header header = 1;
  Status status = 2;
  string state = 3;
  bool pipeline_started = 4;
  bool calibration_ready = 5;
  bool has_stereo = 6;
  int64 latest_frame_id = 7;
}
```

兼容说明：

- `PoseObservation.pose_matrix_row_major` 继续沿用 Python OpenCV 相机坐标，Unity 仍负责转换到 Unity camera-local 坐标。
- `QuestStereoFrame.header.frame_id` 替代旧 `frame_id` 字段，但 protobuf 内仍可按需要保留直接字段；首版建议统一放 Header。
- `Header.anchor_id` 为未来多 anchor 预留，当前默认 `main`。
- `Header.session_id` 用于区分一次运行会话，避免旧命令或旧帧误关联。

## Python 侧架构设计

核心对象：

- `NatsBus`：封装连接、发布、订阅、request/reply、drain、close、重连日志。
- `MessageRouter`：按 subject 注册 handler，避免散落 `if topic`。
- `CommandRouter`：按 `AnchorCommandRequest.WhichOneof("command")` 注册 command handler。
- `NatsQuestInputBuffer`：把 NATS stereo/camera_info 转成 pipeline 需要的 `get_stereo_frames()`、`get_camera_info()`、`get_calibration()`、`get_input_state()` 接口，作为旧 `QuestReceiver` 的兼容替身。
- `TrackingRuntime`：唯一拥有 pipeline 的运行期对象，负责串行处理帧和命令。
- `AnchorStateMachine`：维护 `BOOTING`、`WAITING_CALIB`、`DETECTING`、`TRACKING`、`RESETTING`、`REACQUIRING`、`ERROR`、`STOPPED`。
- `PosePublisher`：把 `TrackingPipelineOutput` 转成 `PoseObservation` 并发布。

Python 并发模型：

- asyncio event loop 负责 NATS IO。
- NATS subscription callback 只做 protobuf decode 和写 latest buffer / command queue。
- pipeline 的 `run()`、`reset_tracking_state()`、`set_stage()` 由 `TrackingRuntime` 串行调用。
- 不允许多个 handler 直接并发访问 pipeline。
- 如果未来 pipeline 被放到线程中，必须通过单线程 worker + queue 调用，而不是任意 `asyncio.to_thread()` 并发调用。

路由示例设计：

```python
router = MessageRouter()
command_router = CommandRouter()

@router.subscribe("egoanchor.v1.quest.stereo", QuestStereoFrame)
async def on_stereo(msg, ctx):
    ctx.input_buffer.update_stereo(msg)

@router.subscribe("egoanchor.v1.quest.camera_info", QuestCameraInfo)
async def on_camera_info(msg, ctx):
    ctx.input_buffer.update_camera_info(msg)

@command_router.command("reset_tracking")
async def handle_reset(cmd, ctx):
    return await ctx.runtime.enqueue_command(ResetTrackingAction(cmd))

@command_router.command("rerun_pose_estimation")
async def handle_rerun(cmd, ctx):
    return await ctx.runtime.enqueue_command(RerunPoseEstimationAction(cmd))
```

命令处理语义：

- `reset_tracking`：清空 Python tracking 状态；generation++；丢弃旧异步分割结果；发布 `RESET_APPLIED` state event；可同步返回 `applied=true`。
- `rerun_pose_estimation`：等价于 reset + 强制下一帧进入 detect/register；如果 `wait_until_registered=false`，立即返回 accepted；如果 `true`，在限定帧数/超时内等待 `REGISTER` 或 `RE_REGISTER` 后返回。
- `set_stage`：调用 `pipeline.set_stage(stage)`，自动 reset tracking。
- `anchor_control`：首版只实现 `REACQUIRE` 映射到 rerun，`HOLD/SMOOTH/UPDATE` 先作为 Unity 本地控制或返回 `NOT_READY`，避免虚假实现。

错误处理：

- protobuf decode 失败：记录 warning，不响应普通 pub/sub；request/reply 返回 `INVALID_ARGUMENT`。
- pipeline 未启动：命令返回 `NOT_READY`。
- 正在 reset/reacquire：重复命令按 `command_id` 去重；不同命令可能返回 `CONFLICT` 或排队，首版推荐排队 reset、拒绝冲突的 stage/config。
- handler exception：统一转换 `INTERNAL`，记录 `correlation_id`、`command_id`、subject、state。

幂等与重试：

- 服务端维护 `command_id -> AnchorCommandReply` 的 TTL 缓存，例如 30 秒。
- 同一 `command_id` 重复到达，直接返回缓存结果或当前执行状态，不重复 reset。
- Unity 超时后可以用同一 `command_id` 重试一次；不建议无限重试。

可观测性：

- 每条 command 日志包含 `command_id`、`correlation_id`、`anchor_id`、state_before、state_after、latency_ms。
- 每 N 帧 pose 发布统计保留旧指标：fps、depth_valid、phase、latency、drop。
- NATS 连接、重连、订阅 subject、publish 失败要有清晰日志。
- 后续可增加 `egoanchor.v1.debug.metrics` 低频状态消息。

## Unity 侧架构设计

核心组件：

- `NatsConnectionBehaviour`：场景中唯一 NATS 连接对象，管理 URL、client name、connect/dispose、reconnect。
- `NatsMainThreadDispatcher`：NATS 回调线程/Task 到 Unity 主线程的派发队列。
- `NatsPublisher`：发布 protobuf bytes 到 subject。
- `NatsSubscriber`：订阅 subject 并把 protobuf decode 后的事件派发到主线程。
- `NatsRequestClient`：封装 request/reply、timeout、command_id、correlation_id。
- `AnchorCommandApi`：Unity 业务 API，提供 `ResetTrackingAsync()`、`RerunPoseEstimationAsync()`、`SetStageAsync()`、`SetAnchorModeAsync()`。
- `QuestStereoNatsPublisher`：复用当前 QuestStereoEncoder 的图像采集思路，但输出 `QuestStereoFrame` protobuf 并直接 NATS publish。
- `QuestCameraInfoNatsPublisher`：输出 `QuestCameraInfo` protobuf。
- `AnchorPoseReceiver`：订阅 `egoanchor.v1.anchor.pose`，转换为 Unity `Pose`，触发事件给 `FrameAlignedObjectAnchor`。
- `AnchorStateReceiver`：订阅状态事件，驱动 UI/debug 面板。

Unity API 设计：

```csharp
public sealed class AnchorCommandApi : MonoBehaviour
{
    public Task<AnchorCommandReply> ResetTrackingAsync(
        string anchorId = "main",
        bool resetLocalProcessors = true,
        CancellationToken cancellationToken = default);

    public Task<AnchorCommandReply> RerunPoseEstimationAsync(
        string anchorId = "main",
        bool waitUntilRegistered = false,
        CancellationToken cancellationToken = default);

    public Task<AnchorCommandReply> SetStageAsync(int stage, CancellationToken cancellationToken = default);
}
```

Unity reset 行为：

- 用户点击 Unity UI 或交互对象。
- `AnchorCommandApi.ResetTrackingAsync()` 发送 NATS request。
- 如果 reply `accepted/applied`，Unity 同步调用 `FrameAlignedObjectAnchor.ResetAnchorProcessors()`，避免本地 smoother/kalman 保留旧状态。
- 同时监听 `AnchorStateEvent`，当收到 `RESET_APPLIED` 或 `REACQUIRING` 时更新 UI。

Unity 线程原则：

- NATS callback 不能直接访问 Transform、UnityEvent、Texture。
- callback 只 decode protobuf 并入主线程队列。
- 主线程 `Update()` drain 队列，然后触发 UnityEvent 或调用 anchor 组件。

## 避免 if-else 膨胀的机制

Python：

- subject 到 handler 用注册表：`dict[str, MessageHandler]`。
- command oneof 到 handler 用注册表：`dict[str, CommandHandler]`。
- 每个 handler 是小文件小函数，只处理一个消息类型。
- `TrackingRuntime` 提供少量领域方法：`reset_tracking()`、`rerun_pose_estimation()`、`set_stage()`、`process_latest_frame()`。
- `CommandAction` 对象封装动作和参数，runtime 串行执行。

Unity：

- subject 到 receiver component 不再由巨大 switch 管理。
- API 层方法构造具体 protobuf command，不让 UI 直接拼 subject/payload。
- `AnchorPoseReceiver`、`AnchorStateReceiver`、`AnchorCommandApi` 分离，避免一个 MonoBehaviour 同时做连接、解码、业务、UI。

## reset / rerun / anchor control 可扩展流程

`reset_tracking` 首版流程：

1. Unity 生成 `command_id`，发送 `AnchorCommandRequest.reset_tracking`。
2. Python command router 校验状态和参数。
3. runtime 串行调用 `pipeline.reset_tracking_state()`。
4. runtime `generation += 1`，清空 pending rerun 状态。
5. Python 回复 `accepted=true, applied=true, state=DETECTING`。
6. Python 发布 `AnchorStateEvent(state=DETECTING, phase=RESET_APPLIED, generation=...)`。
7. Unity 收到 reply 后 reset local processors；收到 state event 后更新 UI。

`rerun_pose_estimation` 首版流程：

1. Unity 发送 `rerun_pose_estimation(clear_tracking_state=true, wait_until_registered=false)`。
2. Python reset tracking，并设置 `runtime.force_register_generation = generation`。
3. 下一帧 pipeline 自然进入 `WAIT_DETECT` -> `REGISTER`。
4. Python pose event 的 `phase` 体现 `REGISTER` / `RE_REGISTER`。
5. 如果客户端要求等待注册，runtime 在帧循环里完成 promise/future，超时返回 `TIMEOUT`。

`anchor_control` 演进：

- `REACQUIRE`：映射到 rerun。
- `HOLD`：首版建议 Unity 本地停止应用新 pose，Python 继续处理；未来可发给 Python 降低算力。
- `SMOOTH`：首版建议 Unity 本地切换 processor 参数。
- `UPDATE`：恢复应用新 pose。
- 后续 adaptive anchor controller 可以把 motion/reliability/latency 输入到 Unity 或 Python 状态机，但不要在首版声称已经完成。

## 分阶段落地计划

- 新增共享 proto 目录和 `egoanchor.v1` proto 文件。

- 增加生成脚本，但不删除 MessagePack/ZMQ。
- 验证生成的 Python/C# protobuf 类型可编译。

验收：

- Python 能 import generated protobuf。
- Unity `dotnet build EgoAnchor_Unity/Assembly-CSharp.csproj --no-restore` 通过。
- NATS demo 不依赖 JSON，能用 protobuf request/reply 往返一个 `HealthRequest/HealthReply`。

### Phase 1：NATS command overlay，快速替代键盘 r

- 新增 Python `anchor_server` 最小入口，仍可复用旧 pipeline 或以 adapter 包装旧 pipeline。
- 旧 ZMQ stereo/pose 链路继续工作。
- 新 NATS command service 订阅 `egoanchor.v1.anchor.commands`。
- 实现 `reset_tracking`，调用当前 pipeline 的 `reset_tracking_state()`。
- Unity 新增 `AnchorCommandApi.ResetTrackingAsync()` 和一个测试 MonoBehaviour/UI 入口。

验收：

- 不按 Python 键盘 `r`，从 Unity 调用 reset，Python tracking 状态清空并重新 register。
- 旧 ZMQ 图像和 pose 仍保持可用。
- 重复同一 `command_id` 不重复执行 reset。

### Phase 2：NATS state/event 与 health

- Python 发布 `AnchorStateEvent`。
- Unity `AnchorStateReceiver` 订阅并显示状态。
- 实现 `egoanchor.v1.server.health` request/reply。
- 增加 command/status 错误码与日志。

- Unity 能看到 `WAITING_CALIB`、`DETECTING`、`TRACKING`、`RESETTING` 等状态。
- NATS health request 能返回 pipeline_started、calibration_ready、has_stereo、latest_frame_id。

### Phase 3：NATS pose output 替代 ZMQ pose

- Python `PosePublisher` 发布 `PoseObservation` 到 `egoanchor.v1.anchor.pose`。
- Unity `AnchorPoseReceiver` 解码 protobuf pose，并复用当前 OpenCV->Unity 坐标转换与 `FrameAlignedObjectAnchor.ApplyCameraPose()`。
- 旧 `PoseDecoder` 仍保留，场景可选择 ZMQ 或 NATS pose receiver。

验收：

- Unity 使用 NATS pose 也能正确 world anchor 对齐。
- `frame_id` camera pose cache 命中率正常。

### Phase 4：NATS stereo/camera_info input 替代 ZMQ input

- Unity 新增 `QuestStereoNatsPublisher`、`QuestCameraInfoNatsPublisher`。
- Python 新增 `NatsQuestInputBuffer`，提供和 `QuestReceiver` 等价的接口。
- 新 server 使用 NATS input buffer 构建/驱动 pipeline。
- 保留 latest-only drain 语义和延迟统计。

验收：

- 完全使用 NATS stereo + camera_info + pose + commands 跑通端到端。
- 当前默认分辨率/JPEG quality 下 NATS payload 不超过 server max payload，延迟与 ZMQ 基线可接受。
- camera_info cache 保存逻辑仍正常。
- ZMQ 输入发送器和 Python ZMQ receiver 可以在场景/配置中关闭，NATS 链路独立运行。

### Phase 5：统一新入口与逐步弃用旧链路

- 新 Python 入口成为推荐入口，例如 `pixi run python .\src\anchor_server\main.py --config .\config\runtime.toml`。
- runtime.toml 增加 `transport.type = "zmq" | "nats"` 或新配置文件，初期默认可保持旧值，验证稳定后切换默认。
- Unity 场景中添加新 NATS 组件，保留旧组件禁用状态作为回退。
- 协议测试改为 protobuf 合约测试。

验收：

- 新链路覆盖旧链路全部功能。
- 文档/AGENTS 更新当前主线。
- 再单独计划删除旧 ZMQ/MessagePack 代码。

## 风险与缓解

- NATS broker 增加部署依赖：提供本机启动脚本或明确 `nats-server` 启动方式；Unity 连接失败时给出清晰状态。
- Unity Protobuf/NATS IL2CPP 兼容风险：先在 Editor 验证，再 Quest 实机验证；避免依赖反射-heavy serializer。
- 高频图像通过 NATS 的延迟风险：先保留 ZMQ 基线，Phase 4 做 A/B 测试；必要时 stereo 保留 ZMQ，control/pose 使用 NATS，但长期目标仍可统一。
- pipeline 并发访问风险：所有命令必须经 runtime queue 串行执行，不允许 handler 直接改 pipeline。
- command 超时导致重复执行：强制 `command_id` 幂等缓存。
- schema 演进风险：proto 字段只追加不复用编号；废弃字段保留编号 reserved；subject 带 `v1`。

## 首轮实施建议

优先做 Phase 0 到 Phase 1：

- 用 Protobuf 定义 `Header`、`Status`、`AnchorCommandRequest`、`AnchorCommandReply`、`ResetTrackingCommand`、`HealthRequest/Reply`。
- Python 增加新 NATS command service，但暂不迁移 stereo/pose。
- Unity 增加 `AnchorCommandApi`，从交互/UI 触发 reset。
- 这样能最快替代 Python 键盘 `r`，同时验证 NATS request/reply、protobuf codegen、幂等、主线程回调这些关键机制。

之后再迁移 pose output，最后迁移高频 stereo input。这个顺序风险最低，因为 reset/control 是当前最迫切的交互迁移需求，且不会一开始冲击高频图像链路和 FoundationPose 性能。最终目标不是长期混合协议，而是完成 Phase 4/5 后让 NATS + Protobuf 独立承载整条 Unity/Python 主链路。
