# EgoAnchor v2 NATS/Protobuf 架构重构规划

## 目标与边界

本次重构目标不是直接替换旧链路，而是新增一条可并行运行、可验证、可逐步接管的 v2 通信与服务框架。

核心目标：

- 将 Python 端 `r` 键触发的 `pipeline.reset_tracking_state()` / 重新检测 pose 流程迁移为 Unity 侧可调用 API。
- 支持 Unity -> Python 的控制命令，例如 reset、reacquire / rerun pose estimation、anchor control。
- 支持 Python -> Unity 的 pose 结果、anchor 状态事件、心跳、错误状态发布。
- 建立消息定义、注册、路由、handler、状态管理、异步执行、错误处理、重试、幂等、日志可观测性的统一框架。
- 避免未来在 server 主循环中继续堆叠 `if topic == ...` / `if command == ...` 逻辑。
- 保留旧 ZMQ/MessagePack 主线作为回退版本，v2 新代码完成测试后再切换默认入口。

明确边界：

- 不直接修改旧 `object_tracking_server.py`、旧 `QuestReceiver`、旧 Unity `PayloadSender/PayloadReceiver` 作为第一步。
- v2 不在 handler 回调里直接操作 GPU pipeline；pipeline 状态必须由单一 runtime 顺序拥有。
- 第一阶段使用 NATS Core，不使用 JetStream 持久化；实时视觉流应 latest-only、低延迟、可丢旧帧。
- Protobuf 是跨语言协议唯一来源；不再使用 JSON 作为正式协议。

## 当前项目现状

从当前仓库读取到的事实：

- 旧主链路完整存在：Unity `PayloadSender/PayloadReceiver` + ZMQ PUB/SUB + MessagePack。
- Python 主入口为 `EgoAnchor_Python/src/object_tracking_server.py`，当前负责配置、pipeline 创建、主循环、pose 编码发布、debug 热键和统计。
- Python pipeline 为 `EgoAnchor_Python/src/pipeline/quest_object_tracking_pipeline.py`，已有明确 API：`start()`、`run()`、`stop()`、`set_stage()`、`reset_tracking_state()`。
- 当前 `r` 键语义是调用 `pipeline.reset_tracking_state()`，随后 pipeline 在后续帧中等待有效 mask/depth 并重新 register。
- Python `QuestReceiver` 当前在 `EgoAnchor_Python/src/modules/quest_io.py` 中按 topic latest-drain 接收 `quest_stereo` 和 `quest_camera_info`。
- Unity anchor 应用链路已具备 frame-aligned 机制：`QuestStereoEncoder.OnFrameEncoded(frame_id, cameraPose)` -> `FrameAlignedObjectAnchor.HandleFrameEncoded()` 缓存相机 pose -> Python 回包带 `frame_id` -> `ApplyCameraPose()`。
- Unity 已安装 `NATS.Net` 和 `Google.Protobuf` NuGet 包，`Assets/Scripts/Nats` 中已有 JSON/NATS 概念验证。
- 当前仓库尚未存在共享 `.proto`、`EgoAnchor_Protocol/`、Python `egoanchor_v2/` 目录；这些应作为 v2 新增内容。

## NATS + Protobuf 可行性判断

结论：NATS + Protobuf 适合 EgoAnchor 下一阶段的控制命令、事件驱动、双向消息通信和服务解耦；对高频 stereo 图像流也可行，但必须采用 Core NATS + application-level latest-only + 严格丢旧帧策略，不能把 NATS 当作无限队列或持久化日志。

适合点：

- NATS 原生支持 publish/subscribe、request/reply、queue group，可自然覆盖实时流、命令、状态事件、服务拆分。
- subject 本身就是路由键，适合把 `quest.stereo`、`quest.camera_info`、`cmd.anchor.reset`、`pose.result`、`anchor.status` 分开管理。
- request/reply 比 ZMQ PUB/SUB 更适合 reset/reacquire 这类需要 ack、timeout、retry、request_id 的交互。
- Protobuf 比 MessagePack + 手写字段契约更适合跨语言演进，字段号、保留字段、生成代码、类型检查都更可靠。
- 后续多个 Unity 客户端、多个 Python 服务模块、状态监控工具接入时，NATS 的解耦优势明显。

风险点：

- 高频大 payload 图像流会增加 NATS broker、客户端序列化和 GC 压力；必须测试 Quest 端实际吞吐和延迟。
- NATS 引入独立 broker，部署、启动顺序、连接恢复、端口、日志都会比 ZMQ 复杂。
- Unity IL2CPP/Android 下 NATS.Net 与 Google.Protobuf 需要真机验证，不能只用 Editor 测试。
- Core NATS 默认是 at-most-once，不保证消息必达；这与实时流匹配，但命令层需要应用级 request_id、ack、retry、幂等。
- NATS request 超时不等于命令失败；可能是 reply 丢失、服务未连接、handler 慢或 broker 问题，客户端 API 要区分。

与 ZMQ + MessagePack 取舍：

- ZMQ + MessagePack 优点：依赖少、低开销、当前已稳定、适合单 Unity 单 Python 直连实时流。
- ZMQ + MessagePack 缺点：缺 request/reply 语义、服务发现弱、路由/handler 需自建、扩展多命令后容易 if-else 膨胀。
- NATS + Protobuf 优点：消息拓扑清晰、命令 ack 自然、跨服务扩展强、协议演进好、可观测性和调试工具更成熟。
- NATS + Protobuf 缺点：多一个基础设施组件，实时性能需验证，Unity 真机兼容性需额外测试。

建议：v2 采用 NATS + Protobuf；旧 ZMQ 继续保留到 v2 在实际 Quest 端完成性能和稳定性验证。

## 推荐通信架构分层

建议分为 5 层，避免业务、协议、传输、pipeline 混杂：

1. 协议层 `EgoAnchor_Protocol/`

- 只定义 `.proto`、subject registry、生成脚本和协议契约测试。
- 不包含 Python/Unity 业务逻辑。
- 所有 subject、消息类型、通信模式、latest-only、是否需要 ack 在一个 registry 文件里集中声明。

2. 传输层 Python `egoanchor_v2/transport/` 与 Unity `Scripts/EgoAnchor/V2/Transport/`

- 只负责 NATS 连接、发布、订阅、request/reply、重连、取消、统计。
- 不理解 pose、anchor、pipeline 语义。

3. 路由层 Python `egoanchor_v2/routing/` 与 Unity `V2/Routing/`

- 根据 subject registry 自动把 subject 绑定到 protobuf 类型与 handler。
- 提供注册器，避免 server 主循环写 if-else。

4. 应用层 Python `egoanchor_v2/runtime/` 与 Unity `V2/Client/`

- Python 侧包含 `LatestInputStore`、`CommandQueue`、`TrackingRuntime`、`AnchorStateMachine`。
- Unity 侧包含 `EgoAnchorClient`、`AnchorControlApi`、`PoseResultReceiver`、`FramePoseCacheBridge`。

5. 领域层现有 pipeline / anchor

- Python 侧复用现有 `QuestObjectTrackingPipeline` 的算法能力，但逐步拆出输入源接口，使其可从 NATS latest store 读取帧。
- Unity 侧复用 `FrameAlignedObjectAnchor` 的 frame_id 对齐和 processors，不把网络协议逻辑塞进 anchor transform 组件。

## Protobuf 消息结构建议

目录建议：

```text
EgoAnchor_Protocol/
  proto/egoanchor/v1/common.proto
  proto/egoanchor/v1/quest.proto
  proto/egoanchor/v1/anchor.proto
  subjects.v1.json
  tools/generate_proto.ps1
  generated/python/...
  generated/csharp/...
```

`common.proto`：

- `MessageHeader`
- `CommandAck`
- `Vec3`
- `Quat`
- `Pose3D`
- `Matrix4x4`
- `ErrorInfo`
- `TimingStats`

`MessageHeader` 建议字段：

- `string message_id`
- `string request_id`
- `string session_id`
- `string client_id`
- `string anchor_id`
- `int64 frame_id`
- `int64 unity_frame`
- `double sender_mono_ms`
- `double created_unix_ms`
- `string schema_version`

说明：

- `message_id`：每条消息唯一，用于日志追踪。
- `request_id`：命令级幂等键；同一命令重试必须保持相同 request_id。
- `anchor_id`：预留多 anchor。
- `frame_id`：视觉帧对齐核心字段。
- `sender_mono_ms`：继续保留延迟估计，但不要跨设备直接当真实 wall-clock 延迟。

`quest.proto`：

- `QuestStereoFrame`
- `QuestCameraInfo`
- `LensPose`

`QuestStereoFrame` 字段建议：

- `MessageHeader header`
- `bytes left_image_jpeg`
- `bytes right_image_jpeg`
- `int32 left_width`
- `int32 left_height`
- `int32 right_width`
- `int32 right_height`
- `int32 jpeg_quality`

`QuestCameraInfo` 字段建议以当前 `QuestCameraInfoMsg` 为基准迁移，保留：

- supported 状态
- left/right fx/fy/cx/cy
- distortion
- baseline_m
- sensor/active/requested/current size
- max_framerate
- left/right lens pose

`anchor.proto`：

- `PoseResult`
- `AnchorStatusEvent`
- `ServerHeartbeat`
- `ResetTrackingRequest`
- `ReacquireAnchorRequest`
- `AnchorControlRequest`

`PoseResult` 字段建议：

- `MessageHeader header`
- `bool has_pose`
- `Matrix4x4 pose_matrix_cv_camera`
- `string phase`
- `int32 stage`
- `int32 det_count`
- `float depth_valid_ratio`
- `float fps`
- `TimingStats timing`
- `ErrorInfo last_error`

`CommandAck` 字段建议：

- `MessageHeader header`
- `bool accepted`
- `bool duplicate`
- `string status`
- `string message`
- `ErrorInfo error`
- `double accepted_mono_ms`

命令 ack 语义：

- `accepted=true` 只表示命令已被 server 接受并入队或已幂等识别，不表示已产生新 pose。
- 命令实际执行状态通过 `AnchorStatusEvent` 发布，例如 `RESET_APPLIED`、`REACQUIRE_STARTED`、`REACQUIRE_SUCCEEDED`、`REACQUIRE_FAILED`。

## Subject 设计建议

使用稳定、分层、可过滤的 subject：

```text
egoanchor.v1.quest.stereo
egoanchor.v1.quest.camera_info
egoanchor.v1.pose.result
egoanchor.v1.anchor.status
egoanchor.v1.server.heartbeat
egoanchor.v1.cmd.anchor.reset
egoanchor.v1.cmd.anchor.reacquire
egoanchor.v1.cmd.anchor.control
```

`subjects.v1.json` 建议包含：

```json
{
  "egoanchor.v1.quest.stereo": {
    "direction": "unity_to_python",
    "protobuf": "egoanchor.v1.QuestStereoFrame",
    "mode": "pubsub",
    "latest_only": true
  },
  "egoanchor.v1.cmd.anchor.reset": {
    "direction": "unity_to_python",
    "protobuf": "egoanchor.v1.ResetTrackingRequest",
    "reply": "egoanchor.v1.CommandAck",
    "mode": "request_reply",
    "idempotent_by": "header.request_id"
  }
}
```

设计原则：

- 高频输入流：pub/sub + latest-only。
- 输出 pose：pub/sub + latest-only。
- 状态事件：pub/sub，不要求 latest-only，可由客户端保留近期历史。
- 控制命令：request/reply + request_id 幂等。
- 后续多服务：可引入 queue group，但 tracking runtime 初期只能有一个 active worker。

## 消息类型与领域事件划分

建议区分 4 类消息：

1. Stream Input

- `QuestStereoFrame`
- `QuestCameraInfo`
- 特点：高频或低频输入状态，latest-only，可丢旧帧，不需要 ack。

2. Command

- `ResetTrackingRequest`
- `ReacquireAnchorRequest`
- `AnchorControlRequest`
- 特点：Unity 主动发起，需要 request_id、timeout、ack、幂等。

3. Result

- `PoseResult`
- 特点：Python pipeline 输出，Unity 消费最新 pose；`has_pose=false` 是合法状态。

4. Domain Event

- `AnchorStatusEvent`
- `ServerHeartbeat`
- 特点：反映状态机迁移、错误、能力、运行状态；用于 UI、日志、调试和后续监控。

不要把所有东西塞进 `PoseResult`。`PoseResult` 负责逐帧结果，`AnchorStatusEvent` 负责流程状态变化。

### Python 核心组件职责

`subjects.py`：

- 加载 `EgoAnchor_Protocol/subjects.v1.json`。
- 提供 `SubjectSpec`：subject、protobuf type、mode、latest_only、reply type。
- 防止 subject 字符串散落在代码中。

`protobuf_registry.py`：

- 将 proto full name 映射到 Python `*_pb2` 类。
- 提供 `parse_message(subject, bytes)` 和 `serialize_message(message)`。

`nats_client.py`：

- 封装 `nats-py` connect、publish、subscribe、request、close。
- 统一记录连接状态、重连、错误。
- 依赖懒加载，便于未安装 NATS 时协议单测仍可运行。

`nats_router.py`：

- 根据 subject registry 订阅 subject。
- 收到消息后：查 spec -> parse protobuf -> 调 handler -> request/reply 时返回 ack。
- 不包含 pipeline 业务逻辑。

`latest_input_store.py`：

- 按 subject 保存最新输入。
- `quest.stereo` 使用 frame_id 去重，只保留最新。
- `quest.camera_info` 保存最新版本号。
- 对外提供快照读取：`get_latest_stereo()`、`get_camera_info()`、`get_input_state()`。

`command_queue.py`：

- handler 快速校验后把命令入队。
- 支持优先级：reset/reacquire 高于普通 control。
- 支持 latest/collapse 策略：短时间重复 reset 可合并。

`command_dedup.py`：

- 以 `request_id` 记录命令接收结果。
- 同一 request_id 重试返回相同 ack，不重复执行。
- 设置 TTL，避免无限增长。

`tracking_runtime.py`：

- 唯一拥有 pipeline 和 anchor state machine 的对象。
- 主循环顺序处理：drain command queue -> 读取 latest input -> 跑 pipeline 一帧 -> 发布 pose/status。
- 命令执行必须发生在此 runtime 中，避免 NATS handler 与 pipeline 并发访问 GPU/状态。

`anchor_state_machine.py`：

- 管理 anchor 状态：`STOPPED`、`WAITING_INPUT`、`WAITING_CALIBRATION`、`DETECTING`、`REGISTERING`、`TRACKING`、`LOST`、`REACQUIRING`、`ERROR`。
- 将 pipeline phase 映射为稳定领域状态事件。
- reset/reacquire/control 命令只触发状态迁移，不直接散落在主循环 if-else。

`pose_result_encoder.py`：

- 将 `TrackingPipelineOutput` 转为 `PoseResult` protobuf。
- 保持 OpenCV camera coordinate 约定，Unity 侧继续负责转换到 Unity 坐标。

### Python handler 编排模式

建议采用注册表/装饰器，不在 server 主循环写 if-else：

```python
registry = HandlerRegistry()

@registry.request("egoanchor.v1.cmd.anchor.reset")
async def handle_reset(ctx, msg):
    return await ctx.commands.accept_reset(msg)

@registry.subscribe("egoanchor.v1.quest.stereo")
async def handle_stereo(ctx, msg):
    ctx.latest_inputs.put_stereo(msg)
```

handler 原则：

- 只做 parse 后的轻量校验、入 store/queue、返回 ack。
- 不调用 `pipeline.run()`。
- 不调用 `pipeline.reset_tracking_state()`。
- 不执行长耗时 GPU 操作。
- 捕获可预期错误并返回结构化 `CommandAck`。

### Python 异步模型

推荐模型：

- NATS I/O 使用 `asyncio`。
- NATS callbacks 与 tracking runtime 在同一个 event loop 内协作。
- `TrackingRuntime` 是一个长生命周期 async task。
- pipeline 仍可保持同步 API；runtime 每轮调用同步 `pipeline.run()`。
- 如果 `pipeline.run()` 阻塞过长影响 NATS callback，再把 pipeline 主循环放入单独线程，并通过 thread-safe queue 与 NATS I/O 通信。

第一阶段建议：

- 使用单 event loop + 同步 pipeline 调用先落地。
- handler 只做极短操作；如果发现 NATS callback 被 GPU 阻塞，再升级为双线程模型。

长期推荐：

- NATS I/O 线程/loop 独立。
- TrackingRuntime 独立线程拥有 pipeline。
- `LatestInputStore` 和 `CommandQueue` 使用线程安全结构或 `asyncio.Queue` + bridge。

## Python pipeline 接入方案

现有 pipeline 依赖 `QuestReceiver` 主动从 ZMQ 读帧。v2 需要逐步解耦输入源。

最小改造路径：

1. 新增 v2 `NatsQuestInput`，提供与 `QuestReceiver` 相似的接口：

- `start()`
- `stop()`
- `poll_all()`
- `get_stereo_frames()`
- `get_camera_info()`
- `get_camera_info_version()`
- `get_calibration()`
- `get_input_state()`
- `get_stats()`

2. 新增 v2 pipeline builder：

- 复用 `QuestObjectTrackingPipeline`。
- 构造时注入 `camera=NatsQuestInput`，而不是旧 `QuestReceiver`。
- 如类型注解暂不兼容，可先定义 `QuestInputSource` Protocol，后续再整理。

3. 不修改旧 builder：

- `build_quest_object_tracking_pipeline(cfg)` 继续使用 ZMQ `QuestReceiver`。
- 新增 `build_quest_object_tracking_pipeline_v2(cfg, input_source)` 或在 v2 runtime 里显式构造。

4. reset 命令落地方式：

- runtime 收到 `ResetTracking` 命令后调用 `pipeline.reset_tracking_state()`。
- 发布 `AnchorStatusEvent(RESET_APPLIED)`。
- 后续 `pipeline.run()` 自然进入 `WAIT_DETECT` / `REGISTER` / `TRACK`。

5. reacquire 命令落地方式：

- 语义上比 reset 更具体：清除当前 tracking，并强制下一次有效 mask/depth register。
- 当前可先映射为 `pipeline.reset_tracking_state()`。
- 后续如果需要“立即用最新帧重新跑一次 register”，再在 pipeline 增加显式 `request_reacquire(options)` 标志。

### Unity 核心组件职责

`NatsConnection`：

- 管理 NATS URL、连接、重连、Dispose、取消 token。
- 只负责传输，不理解 EgoAnchor 业务。

`QuestStreamPublisher`：

- 替代旧 `PayloadSender` 的 v2 版本。
- 持有多个 stream entry：stereo、camera_info。
- 每个 entry 独立 target FPS。
- 发送 Protobuf bytes 到对应 subject。
- 高频发送要避免每帧过多临时分配。

`AnchorControlApi`：

- 对 Unity 交互层暴露清晰 API：

```csharp
Task<CommandAck> ResetTrackingAsync(string anchorId, CancellationToken ct);
Task<CommandAck> ReacquireAsync(string anchorId, ReacquireMode mode, CancellationToken ct);
Task<CommandAck> SetAnchorControlAsync(AnchorControlRequest request, CancellationToken ct);
```

- 自动生成 request_id。
- 支持 timeout。
- 对 timeout、rejected、transport error 给出不同结果。

`PoseResultReceiver`：

- 订阅 `egoanchor.v1.pose.result`。
- 解码 protobuf。
- `has_pose=false` 时只更新状态，不触发 pose 应用。
- `has_pose=true` 时将 OpenCV pose 转 Unity pose，并触发 UnityEvent 或 C# event。

`FrameAlignedAnchorBridge`：

- 连接 v2 `QuestStreamPublisher` 的 frame encoded event 与现有 `FrameAlignedObjectAnchor.HandleFrameEncoded()`。
- 连接 `PoseResultReceiver` 与 `FrameAlignedObjectAnchor.ApplyCameraPose()`。
- 保持 anchor transform 逻辑与网络逻辑分离。

### Unity 主线程规则

- NATS 接收 callback 可能不在 Unity 主线程。
- 任何 UnityEngine API、Transform、UnityEvent 调用必须切回主线程。
- 建议实现 `UnityMainThreadDispatcher` 或在 `Update()` drain 一个线程安全队列。
- `PoseResultReceiver` 后台只解码和入队，主线程再触发事件。

## Reset / Rerun Pose / Anchor Control 机制设计

### ResetTrackingRequest

语义：清空当前 tracking 状态，停止使用旧 pose，等待后续帧重新检测/register。

字段建议：

- `MessageHeader header`
- `bool clear_filters`
- `bool clear_anchor_pose`
- `string reason`

执行：

- Python runtime 调用 `pipeline.reset_tracking_state()`。
- 可选发布 `PoseResult(has_pose=false, phase="RESET")`。
- 发布 `AnchorStatusEvent(RESET_APPLIED)`。
- Unity 收到 ack 后可重置 smoother/kalman filter。

### ReacquireAnchorRequest

语义：主动重新获取 anchor，面向“重新检测 pose”的用户交互 API。

字段建议：

- `MessageHeader header`
- `enum ReacquireMode { NEXT_VALID_FRAME = 0; LATEST_FRAME_IF_AVAILABLE = 1; FORCE_DETECT = 2; }`
- `bool clear_tracking_first`
- `string prompt_override`
- `double timeout_ms`

第一阶段实现：

- `clear_tracking_first=true` 时等同 reset。
- 设置 runtime 状态为 `REACQUIRING`。
- 后续 pipeline 一旦输出 `REGISTER` 或 `RE_REGISTER` 且 `has_pose=true`，发布 `REACQUIRE_SUCCEEDED`。
- 超过内部超时未成功，发布 `REACQUIRE_FAILED`，但 request/reply ack 仍只表示命令已接受。

### AnchorControlRequest

语义：统一承载运行控制，不要为每个小开关新增一个 command subject。

可覆盖：

- pause/resume tracking。
- set stage。
- set prompt。
- enable/disable smoothing。
- set hold mode。
- clear anchor。

设计建议：

- 初期只实现 `SET_STAGE`、`PAUSE`、`RESUME`。
- 高风险配置修改不要第一阶段开放，例如动态换 mesh/model。

## 状态管理与状态机

建议引入 `AnchorStateMachine`，不要只依赖 pipeline phase 字符串。

状态建议：

- `STOPPED`
- `WAITING_INPUT`
- `WAITING_CALIBRATION`
- `DETECTING`
- `REGISTERING`
- `TRACKING`
- `LOST`
- `REACQUIRING`
- `PAUSED`
- `ERROR`

事件来源：

- 输入状态：是否收到 camera_info/stereo。
- 命令：reset/reacquire/control。
- pipeline output：`phase`、`has_pose`、`depth_valid_ratio`、`det_count`。
- exception：handler/runtime/pipeline 错误。

发布规则：

- 状态变化时发布 `AnchorStatusEvent`。
- 长时间状态不变时由 `ServerHeartbeat` 提供健康信息，不要每帧刷状态事件。
- `PoseResult` 每帧/每有效输出发布，包含 `phase` 供调试。

## 错误处理

错误分层：

1. Transport error

- NATS 连接失败、request timeout、publish failure。
- Unity API 返回 transport-level failure，不应误报为 server rejected。

2. Protocol error

- Protobuf parse 失败、缺 required semantic field、未知 subject。
- Python 记录 warning，命令类返回 `CommandAck(accepted=false, error=INVALID_ARGUMENT)`。

3. Domain error

- anchor_id 不存在、当前状态不允许执行命令、参数非法。
- 返回 rejected ack，并发布 status event。

4. Runtime error

- pipeline exception、模型文件缺失、GPU 错误。
- runtime 进入 `ERROR` 状态，发布 `AnchorStatusEvent(ERROR)` 和 heartbeat。

5. Recoverable tracking failure

- 无 mask、depth 不足、pose 跳变、track lost。
- 不当作 server error；通过 `PoseResult(has_pose=false/phase=...)` 和 status 表达。

## 重试与超时

Unity command API：

- 默认 request timeout：1-2 秒。
- 超时后可重试，但必须复用同一个 `request_id`，直到用户发起新的命令。
- retry 次数建议 1-2 次，不无限重试。
- 若收到 `duplicate=true` ack，视为服务端已处理/已接受该请求。

Python server：

- `CommandDedupStore` 保存 request_id -> ack，TTL 例如 60 秒。
- 重复 request_id 直接返回原 ack，不重复入队。
- 命令入队失败返回 `accepted=false`。
- 命令已接受但后续执行失败，通过 status event 表达。

实时流：

- 不重试。
- 不 ack。
- 丢旧保新。
- 用 frame_id 检测 gap，并在 stats/heartbeat 中上报。

## 幂等性规则

必须幂等的命令：

- reset tracking。
- reacquire anchor。
- pause/resume。
- set stage。

幂等键：

- `header.request_id`。

执行约束：

- 同一 request_id 不重复执行。
- 不同 request_id 即使内容相同，也视为新命令。
- 若客户端不知道上一条是否成功，使用同一 request_id 重试。

状态类命令建议：

- `PAUSE` 在已 paused 时返回 accepted + no-op。
- `RESUME` 在 running 时返回 accepted + no-op。
- `SET_STAGE` 设置到当前 stage 返回 accepted + no-op。

## 日志与可观测性

Python 日志：

- 每条 command 日志包含 `request_id`、`message_id`、`anchor_id`、subject、accepted/rejected、reason。
- 每次状态迁移日志包含 `old_state -> new_state`、原因、frame_id。
- 高频 frame 日志限频输出，沿用现有统计思路。
- parse error 和 handler exception 记录 subject 和错误摘要，不打印大 payload。

Unity 日志：

- command request/reply 记录 request_id、subject、耗时、accepted/status。
- NATS connect/reconnect/disconnect 记录清楚。
- pose receive 日志限频，避免每帧刷屏。

Heartbeat 建议字段：

- server 状态。
- input 是否 ready。
- 最新 stereo frame_id。
- 最新 camera_info version。
- runtime fps。
- publish fps。
- last error。
- command queue length。

调试工具：

- 保留 `try_nats`，但升级为 protobuf smoke tests。
- 增加 `tools/nats_probe.py`，可订阅 pose/status/heartbeat 并打印摘要。

## 避免 if-else 膨胀的机制

核心策略：subject registry + protobuf registry + handler registry + command pattern。

不要这样做：

```python
if subject == "reset":
    pipeline.reset_tracking_state()
elif subject == "camera_info":
    ...
elif subject == "stereo":
    ...
```

应该这样做：

- subject registry 定义 subject -> protobuf -> mode。
- handler registry 定义 subject -> function。
- command handler 只把 protobuf 转为 command object。
- runtime 使用 command object 的 `execute(context)` 或集中 command dispatcher 执行。

命令对象建议：

- `ResetTrackingCommand`
- `ReacquireAnchorCommand`
- `SetStageCommand`
- `PauseTrackingCommand`
- `ResumeTrackingCommand`

每个命令对象包含：

- request_id。
- anchor_id。
- created time。
- params。
- `execute(runtime_context)`。

第一阶段也可不用复杂类，先用 dataclass + dispatcher dict：

```python
COMMAND_EXECUTORS = {
    CommandType.RESET: execute_reset,
    CommandType.REACQUIRE: execute_reacquire,
}
```

## 快速落地的最小闭环

最小闭环建议按这个顺序做：

1. 定义 proto：`ResetTrackingRequest`、`CommandAck`、`PoseResult`、`QuestStereoFrame`、`QuestCameraInfo`。
2. Python v2 smoke server：接 reset request，返回 protobuf ack。
3. Unity `AnchorControlApi.ResetTrackingAsync()`：ContextMenu 能收到 ack。
4. Python latest store：接收 Unity v2 stereo/camera_info protobuf。
5. Python `NatsQuestInput` 适配现有 pipeline。
6. Python `TrackingRuntime`：处理 reset command 并发布 pose result。
7. Unity `PoseResultReceiver`：把 v2 pose 接到现有 `FrameAlignedObjectAnchor`。

这个闭环完成后，Unity 侧交互即可替代 Python `r` 键，同时框架已经具备后续扩展 command/status/event 的基础。

## 关键实现细节建议

### NATS 使用方式

- 高频图像和 pose 使用 Core NATS publish/subscribe。
- 命令使用 Core NATS request/reply。
- 暂不使用 JetStream，除非后续需要记录实验数据、离线回放或可靠事件审计。
- NATS server 配置需要确认 `max_payload` 大于 stereo protobuf payload，建议至少数 MB。
- 客户端禁用或限制无限 pending buffer，应用层仍以 latest-only 控制延迟。

### Protobuf 兼容性

- 字段号一旦发布不要重排。
- 删除字段必须 `reserved` 字段号和字段名。
- message 中可新增 optional 字段保持兼容。
- subject version 使用 `egoanchor.v1.*`；未来破坏性升级用 `v2` subject。

### Unity 内存与性能

- JPEG bytes 仍是主要 payload，Protobuf 包一层的额外开销可接受。
- 高频发布避免每帧构造过多临时对象；先功能正确，再 profile 优化。
- NATS callback 不直接调用 Unity API。
- Quest 真机上优先测试连接稳定性、帧率、GC spike。

### Python 并发安全

- handler 不碰 pipeline。
- pipeline 只由 TrackingRuntime 线程/任务访问。
- 命令队列和 latest input 是唯一跨边界共享状态。
- reset/reacquire 等命令在 frame 边界执行，避免半帧中途修改 pose_estimator。

## 风险与备选方案

风险 1：NATS 图像流性能不满足 Quest 实时需求。

- 备选：短期采用混合架构，ZMQ 继续传 stereo/camera_info，NATS 只传 command/status/pose。
- 长期再优化 NATS payload、压缩质量、分辨率、发送频率或局域网部署。

风险 2：Unity Android/IL2CPP 下 NATS.Net 存在兼容问题。

- 备选：Unity Editor 先完成开发；Quest 真机若 NATS.Net 不稳，评估 WebSocket NATS、原生插件或保留 ZMQ 控制通道过渡。

风险 3：Pipeline 当前强耦合 QuestReceiver。

- 处理：先用接口适配 `NatsQuestInput`，不要大拆 pipeline；等 v2 稳定后再清理类型边界。

风险 4：Command ack 被误解为完成。

- 处理：协议和 Unity API 明确区分 `CommandAck` 与 `AnchorStatusEvent`；reacquire 成功只能通过 status/pose result 判断。

## 最终推荐架构结论

- EgoAnchor 下一阶段应采用 NATS + Protobuf 作为 v2 通信框架，尤其适合 Unity 侧交互控制、request/reply、事件驱动、未来多服务扩展。
- 高频 stereo 流可以纳入 NATS v2，但必须通过 Core NATS + latest-only + 丢旧策略实测验证；不要一开始依赖 JetStream 或可靠队列。
- Python server 应从“主循环中 if 判断消息”演进为“subject registry + protobuf registry + router + handler + command queue + single-owner runtime”。
- Unity 应从“组件直接发消息”演进为“EgoAnchorClient/AnchorControlApi/StreamPublisher/ResultReceiver”，网络 API 与 anchor transform 应用解耦。
- reset/rerun pose estimation 的第一版可直接映射到现有 `pipeline.reset_tracking_state()`，但协议上应设计为 command + ack + status event，给后续更复杂 reacquire 流程留空间。
- 重构应按 v2 新目录逐步实现，不修改旧链路；每一阶段都有 smoke test 和回退路径。
