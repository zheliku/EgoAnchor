你的理解更准确：**静止锚定应当被视为“逐帧锚点合成”的一部分，而不是与锚点合成并列的第三个处理阶段。**

关键在于区分两个层面：

* **实现调度层面**：StaticLock 的运动证据会在候选到达时更新，模式转换和最终位姿会在渲染帧提交。
* **方法功能层面**：StaticLock 决定每个渲染时刻最终输出什么锚点位姿，因此它属于锚点合成策略。

论文结构应优先反映第二个层面，而不是严格复制代码线程或事件回调。

---

## 1. 什么是“锚点合成”

我建议把“逐帧锚点合成”明确界定为：

> 给定已经接纳的世界系观测轨迹、当前运动状态以及渲染时刻 (t_r)，生成应用在该渲染帧实际消费的世界系锚点位姿。

在这个定义下，锚点合成至少包含三个环节：

1. 确定查询时刻 (t_q)；
2. 从时间索引轨迹中得到连续跟踪位姿；
3. 根据运动状态决定最终输出跟踪位姿、锁定位姿或二者之间的过渡结果。

因此：

[
\text{accepted observations}
\rightarrow
\text{tracking trajectory}
\rightarrow
\text{motion-aware output}
\rightarrow
\widetilde T_o^w(t_r).
]

StaticLock 显然位于第三步。

目前手稿把“逐帧输出”和“静止锚定”拆成两个平级小节，容易造成一种错误印象：

> 先完成逐帧输出，然后再额外执行静止锚定。

但从你们的最终输出方程看并不是这样。最终位姿本身就是：

[
\widetilde T_o^w(t_r)=
\begin{cases}
T_{o,\mathrm{lock}}^w, & m(t_r)=\mathsf{Locked},
\widehat T_o^w(t_q), & m(t_r)=\mathsf{Tracking}.
\end{cases}
]

也就是说，**轨迹取值只生成 Tracking 分支的候选输出，StaticLock 决定最终使用哪个分支。** 所以静止锚定不是合成后的附加滤波，而是合成函数内部的模式选择。

# 2. 更准确的概念层级

我认为全文应该形成下面的三级关系。

## 第一层：观测处理

回答：

> 哪些视觉候选能够进入锚点运行时，以及它们在世界坐标系中表示什么？

包含：

* 采集时刻配准；
* VCD 准入；
* 状态估计；
* 写入时间索引轨迹；
* 更新运动状态和 StaticLock 证据。

输出不是应用锚点，而是：

[
\left{
(t_i,\widehat T_o^w(t_i))
\right}
\quad+\quad
\text{runtime state}.
]

## 第二层：锚点合成

回答：

> 在每个渲染时刻，应用实际得到什么位姿？

包含：

* 历史查询时刻；
* Linear/SLERP 轨迹取值；
* Tracking/Locked 模式选择；
* 锁内微调；
* 入锁与解锁；
* 解锁后的接缝过渡。

输出是：

[
\widetilde T_o^w(t_r).
]

因此 StaticLock 属于这一层。

## 第三层：生命周期管理

回答：

> 当前输出是否仍然可信、是否应当保持、降级、隐藏或重新获取？

它不主要决定正常 Tracking/Locked 状态下的位姿数值，而是决定：

* 输出有效性；
* 不确定性；
* Holding/Lost 状态；
* 重新注册与恢复；
* 应用是否继续呈现附着内容。

所以生命周期最好与锚点合成分开。它处理的是**锚点的存在与可信状态**，StaticLock 处理的是**锚点位姿如何输出**。

# 3. 我建议的第3.3节结构

最清晰的结构不是当前的：

* 观测更新
* 逐帧输出
* 静止锚定
* 生命周期管理

而是：

## 3.3 锚定运行时

### 3.3.1 观测配准与准入

内容依次为：

* 采集时刻配准；
* 世界系复合；
* VCD准入；
* 状态估计与轨迹控制点。

这里最后补一句即可：

> 每个接纳观测同时更新运动状态及静止锚定所需的进入和释放证据。

不需要在这里展开 StaticLock。

### 3.3.2 逐帧锚点合成

这一节内部自然分成三个加粗段落：

**时间索引轨迹取值。**
定义 (t_q) 和 (\widehat T_o^w(t_q))。

**运动状态感知输出。**
定义 Tracking/Locked 两种输出模式，以及最终位姿方程。

**静止锁定与释放。**
解释进入锁定、锁内微调、解锁证据和接缝过渡。

这样 StaticLock 的全部内容仍然保留，但概念归属更准确。

### 3.3.3 生命周期管理

解释：

* Tracking；
* Buffered/Holding；
* FrozenUncertain；
* Lost；
* Reacquisition；
* 输出可信度。

### 3.4 运行时流程

Algorithmic Outline 总结两类事件：

* 候选到达；
* 渲染刷新。

# 4. 为什么这种结构比“两个更新通路”更适合论文

“两类事件”是事实，但不是论文的核心方法分解。

如果按代码执行方式组织论文，就会出现你现在遇到的问题：

* StaticLock 证据在候选到达时更新；
* StaticLock 位姿在渲染时输出；
* 入锁请求由一侧产生、另一侧提交；
* 生命周期计时由观测更新、状态表现由渲染输出。

于是任何完整机制都横跨两类事件，很难归入“观测通路”或“渲染通路”。这正说明“两个通路”只适合作为 Algorithmic Outline 的调度说明，不适合作为方法章节的主要分类。

按功能组织后则非常自然：

[
\boxed{\text{观测处理}}
\rightarrow
\boxed{\text{锚点合成}}
\rightarrow
\boxed{\text{生命周期管理}}
]

其中：

* 观测处理建立可信的世界系轨迹；
* 锚点合成生成逐帧位姿；
* 生命周期决定该位姿当前以何种可信状态交付应用。

代码中它们可以异步交错，论文中不需要因此打乱概念层级。

# 5. “静止锚定”在锚点合成中的精确位置

还可以进一步区分：

## 轨迹合成不是完整的锚点合成

Linear/SLERP 得到的是：

[
\widehat T_o^w(t_q),
]

它只是一个连续的**跟踪轨迹位姿**。

它尚未考虑：

* 物体是否已静止；
* 是否应保持锁定位姿；
* 是否正在解锁过渡；
* 当前生命周期是否允许正常交付。

真正的锚点输出是：

[
\widetilde T_o^w(t_r)
=====================

\mathcal S!\left(
\widehat T_o^w(t_q),
T_{o,\mathrm{lock}}^w,
m(t_r)
\right),
]

其中 (\mathcal S) 表示运动状态感知的输出策略。

因此可以建立很清楚的术语层级：

* **轨迹取值 / trajectory sampling**：得到连续跟踪位姿；
* **锚点合成 / anchor synthesis**：结合 Tracking/Locked 状态得到最终位姿；
* **锚点交付 / anchor delivery**：结合生命周期提供位姿与可信度。

这一层级会让公式含义明显更清楚。

---

# 6. StaticLock的进入与解锁证据是否也属于锚点合成？

属于，但要区分“状态更新发生在哪里”和“机制属于什么”。

例如 CUSUM 是在新观测到达时计算的，但它存在的唯一目的，是决定未来的锚点输出模式。它不是观测质量验证，也不是轨迹估计本身。

所以在方法分类上，它属于 StaticLock／锚点合成；在 Algorithm 中，它列在“候选到达时更新证据”。

可以用一句话解决这种表面矛盾：

> 静止锚定是逐帧锚点合成中的运动状态感知输出策略。其运动证据随接纳观测更新，而模式转换和最终输出在渲染帧边界提交。

这句话已经准确表达了你们实现，不需要发明“跨轴状态”。

# 7. 是否还需要单独保留“静止锚定”小标题

有两个可行方案。

## 方案A：作为3.3.2内部加粗段落

这是我更推荐的：

### 3.3.2 逐帧锚点合成

* **轨迹取值。**
* **静止锚定。**
* **模式转换。**

优点是概念层级最干净，也减少小节数量。

## 方案B：保留三级小节

如果 StaticLock 公式和文字确实较长，可以写：

### 3.3.2 逐帧锚点合成

#### 3.3.2.1 时间索引轨迹

#### 3.3.2.2 静止锚定

但 IEEE VR 双栏论文通常不宜出现过深标题层级。你们可以通过加粗行内标题达到同样效果。

不建议继续让“逐帧输出”和“静止锚定”成为同一级别的两个独立过程。

# 8. 生命周期是否也是锚点合成的一部分？

广义上可以说是，但论文中最好不要这样归类。

原因是生命周期主要改变的是：

[
(\widetilde T_o^w(t_r),,q(t_r)),
]

其中 (q(t_r)) 是锚点的有效性或可信状态。

StaticLock主要决定第一项——位姿；生命周期主要决定第二项——输出状态，并在 Holding/Lost 时约束第一项是否继续沿用。

因此最清楚的表达是：

> 逐帧锚点合成确定“输出在哪里”，生命周期管理确定“该输出当前是否以及如何被应用使用”。

两者都属于锚定运行时，但功能不同。

---

# 9. 对摘要和贡献的影响

采用这一结构后，摘要可以改成：

> 锚定运行时通过采集时刻世界配准和VCD准入建立可信的时间索引轨迹，并结合历史轨迹取值与运动状态感知的静止锚定合成逐帧位姿，由分级生命周期管理短时失效与恢复。

这里层级非常清楚：

1. 建立轨迹；
2. 合成位姿；
3. 管理生命周期。

贡献2也可以写成：

> **VCD位姿验证与状态感知锚定运行时：**VCD依据可视度、颜色和深度一致性限制错误候选进入轨迹；锚定运行时按采集时刻恢复世界坐标语义，并通过时间索引轨迹取值和运动状态感知的静止锚定生成逐帧对象位姿，由分级生命周期定义遮挡、失效与恢复期间的交付行为。

比当前把所有机制平铺在一句中更有结构。

## 结论

你的判断成立，而且它解决了当前第3.3节最根本的分类问题：

> **静止锚定不是位于“逐帧输出”之后的独立模块，而是逐帧锚点合成中的状态感知输出策略。**

最终推荐的概念结构是：

[
\boxed{
\text{观测配准与准入}
\rightarrow
\text{逐帧锚点合成}
\rightarrow
\text{生命周期管理}
}
]

其中逐帧锚点合成包括：

[
\boxed{
\text{历史轨迹取值}
+
\text{Tracking/Locked模式选择}
+
\text{静止锁定、释放与过渡}
}
]

“两类事件驱动处理”只需要在运行时流程和算法中交代，不应承担第3章的主要方法分类。
