有。经过这一轮更严格的检索，我需要修正上一轮一个过于简单的判断：

**“插值”本身绝对不是 EgoAnchor 的新颖点，而且 XR 领域确实存在与你们思想相当接近的“故意看过去、在两个已知状态之间插值”的方法。**
但截至我这轮对 XR、tracking、state estimation 和 dynamic-object trajectory 文献的定向检索，**我还没有找到与 EgoAnchor 完全相同的组合：针对异步零样本真实物体 6DoF 观测，先恢复 capture-time world semantics，再基于已接纳世界系观测建立轨迹，根据观测年龄自适应选择历史查询时刻，并用 position interpolation + SLERP 生成逐渲染帧 object anchor，同时明确用 lag–trajectory-fidelity trade-off 来设计和评价。** 这个“组合与问题定义”才是比较安全的贡献位置，而不是 interpolation 本身。

### 1. XR 目前主要有哪些时间处理路线？

我建议不要把相关工作简单分成“prediction vs. ATW”。更准确的谱系是：

| 类别                                             |       时间方向 | 核心思想                                     | 与 EgoAnchor 的关系                                                    |
| ------------------------------------------------ | -------------: | -------------------------------------------- | ---------------------------------------------------------------------- |
| **Prediction / extrapolation**             |         向未来 | 根据历史速度/运动模型预测显示时刻状态        | EgoAnchor 实验二的直接对立策略                                         |
| **Filtering / state estimation**           |       当前附近 | 抑制噪声、估计连续状态，常伴随额外 lag       | 你们的 KF / One-Euro 属于这一层，但不是最终时序策略                    |
| **Historical pose lookup / interpolation** |         向过去 | 查询过去某时刻，在已有样本间插值             | **与 EgoAnchor 很接近**                                          |
| **Buffered / delayed interpolation**       |         向过去 | 主动增加显示延迟，使查询落入两个已知状态之间 | **原理上与 EgoAnchor 最接近**                                    |
| **Fixed-lag / continuous-time smoothing**  |       重估过去 | 保留一段历史窗口，利用后来的测量改善过去状态 | 概念相关，但**不是你们当前算法**                                 |
| **Late-stage reprojection / time warp**    | 向最新显示时刻 | 在渲染后用更新的头姿重投影图像               | ATW；与 EgoAnchor 的机制不同                                           |
| **Delay alignment / stream buffering**     |       对齐多流 | 延迟较快的数据流，使异步数据同时呈现         | 与你们“接受额外 lag 换一致性”思想相关，但通常不做 pose interpolation |

下面几个先例对你们尤其重要。

## 2. 最关键的发现：OpenXR 本身就明确支持“历史位姿 + 插值”

OpenXR 1.1.61 的规范非常值得你们引用。它明确规定，应用可以按一个给定 `XrTime` 查询 space/view 的 pose；查询时间既可以在未来，也可以在过去。对于**过去的时间点**，规范明确指出返回值可以来自 **interpolated historical data**，而且 runtime 必须保留一定窗口的历史数据并在需要时进行 interpolation。相反，未来时间则使用 prediction。([Khronos Registry][1])

这非常重要，因为它证明：

> **“给定一个历史 query time，在已有 pose samples 之间做插值，以获得该时刻 pose”已经是 XR runtime 中明确存在的时间语义。**

所以论文不能暗示“XR runtime 通常只做 prediction，而我们首次提出 interpolation”。

但 OpenXR 与你们仍有明显区别：OpenXR讨论的是 runtime 已经管理的 tracked spaces/views 的**时间查询接口与历史 pose retrieval**；它没有解决你们的异步视觉 object observation 如何由相机系恢复为采集时刻世界系、哪些低质量 object poses 应被接纳、历史 query lag 应如何根据视觉处理延迟自适应变化，以及这种策略用于动态真实物体 anchor 时的稳定性–响应性权衡。([Khronos Registry][1])

这篇/这个规范我认为你们 **Related Work 应该新增引用**。

## 3. 更接近你们的：XR 中确实有“故意延迟 + 在过去状态之间插值”

我找到一个对你们尤其需要正面处理的工作：**Harmonize**，发表于 *Virtual Reality*。

它解决网络化 AR/VR shared environment 中低频 server state update 的问题。服务器状态只有约 10–20 Hz 时，客户端不是把最后状态直接保持到下一状态，而是使用**过去的 entity states，在最近收到的两个状态之间平滑插值 position 和 orientation**。论文直接称其为 **entity interpolation**，而且明确指出代价是：用户看到的是 **past state rather than current state**。([Springer][2])

这与 EgoAnchor 的基本思想：

[
t_q=t_r-\Delta,\qquad
t_i\leq t_q\leq t_{i+1},
]

然后在两个已经到达的状态之间做 interpolation，

实际上是**同一个大的时间设计范式**：

> **宁可主动增加一定 presentation lag，也让渲染查询落在两个已知状态之间，从而避免 extrapolation。**

因此，这一点我们不能回避。

不过两者的问题仍然相当不同：

**Harmonize：**

network/server snapshot
→ buffered past entity states
→ interpolation
→ remote/virtual entity presentation.

**EgoAnchor：**

image captured at (t_f)
→ asynchronous zero-shot object pose arrives at (t_a)
→ recover capture-time world pose
→ reliability admission
→ filtered time-indexed physical-object trajectory
→ **adaptive historical query time**
→ SE(3) interpolation
→ render-time physical object anchor.

所以我认为可以非常安全地说：

> delayed/entity interpolation 已存在于 networked XR；EgoAnchor 并不提出 interpolation 本身，而是将 **capture-time-corrected, reliability-controlled object observations** 组织成一个可供 MR runtime 自适应历史查询的对象轨迹。

这个表述反而比“我们发明了一种时序插值”强。

## 4. XR 中还有“主动增加 delay 来换 temporal alignment”，甚至不做 interpolation

另一个很有价值的先例是 *Full body video-based self-avatars for mixed reality*。

作者发现 passthrough stereo feed、头部运动以及网络返回的 segmentation mask 存在不同延迟，因此使用 **delay alignment buffer**：把 camera pose 放入 buffer，并故意延迟显示；此外又使用 frame buffer，把彩色图像延迟到 segmentation mask 到达，从而让二者同时显示。也就是说，它非常明确地采用：

> **增加一个可控延迟，以换取不同数据流之间的时间一致性。**

它不等同于你们——没有在两个 object poses 之间插值——但证明“deliberate latency for temporal consistency”在 MR 中本身已有先例。([Springer][3])

这也是为什么我现在不推荐把 EgoAnchor 的策略描述为单纯的 **latency compensation**。

因为“compensation”在 XR 文献里往往意味着“减少 latency 所产生的 spatial error”，而你们恰恰主动引入额外的 presentation lag。

更准确的是：

> **temporal alignment / latency handling / latency–fidelity trade-off**

# 5. Prediction 是另一条成熟路线，而且与你们构成真正的技术对立

AR 的 head-motion prediction 至少可以追溯到 Azuma 和 Bishop 的 SIGGRAPH 1994/1995 工作；其核心就是预测未来 head pose，以抵消 sensing/rendering latency 导致的 dynamic registration error。Azuma 后续还专门发表了 *A Frequency-Domain Analysis of Head-Motion Prediction*，并以 *Predictive Tracking for Augmented Reality* 为博士论文主题。([Ronald Azuma][4])

现代视觉 tracking 中也仍然是这个方向。例如 ICCV 2023 的 PVT++ 明确把 processing latency 当成 tracking problem，并预测未来 target state；也就是说，视觉结果到达时已经过时，因此尝试把它**推到现在/未来**。([开源访问][5])

工业 MR 中也有相同路线。一项针对 Mixed-Reality-in-the-Loop simulation 的研究估计 end-to-end latency，然后利用过去位置序列预测真实系统在当前显示时刻的位置，以降低 moving virtual component 的 registration error。([Springer][6])

这实际上正是你们 Experiment 2 应该强调的 theoretical contrast：

[
\boxed{\text{Extrapolation: }t_q\approx t_r,;\text{unknown future state}}
]

versus

[
\boxed{\text{Delayed interpolation: }t_q<t_r,;\text{two known states}}
]

前者以**预测风险换低 latency**；后者以**已知 latency 换 trajectory fidelity**。

你们现在实验结果的意义也就更清楚了：不是证明 “linear interpolation 比 Kalman 好”，而是在真实异步 visual-object stream 下证明了这两个 **temporal operating points** 的实际 trade-off。你们现稿中外推降低有效时延，却使 lag-aligned trajectory residual 明显增大的结果，正适合支撑这个论点。

# 6. ATW 与你们到底什么关系？——现在可以明确回答：**不是同类算法**

ATW 所属的历史可以追溯到 **post-rendering 3D warping**：场景已经从一个 viewpoint 渲染完成后，根据更新后的 viewpoint 对已有图像进行 warp，而不用重新做完整 scene rendering。([数字对象标识符][7])

IEEE VR 的低时延显示研究也采用“post-rendering offset + just-in-time tracking update”来尽可能缩短 motion-to-photon latency。([IEEE VR][8])

所以两者在时间方向上甚至可以说是相反的：

[
\text{ATW: old rendered image}
;\longrightarrow;
\textbf{push forward toward latest head pose}
]

而 EgoAnchor：

[
\text{available object trajectory}
;\longrightarrow;
\textbf{query backward at }t_r-\Delta
]

因此：

**ATW 不应该作为 EgoAnchor historical interpolation 的直接 prior。**

它可以留在 Related Work 中，作用只是说明 **XR display latency compensation** 的另一层技术；但不要形成“prediction vs ATW，然后 EgoAnchor属于ATW这一侧”的叙事。

# 7. Tracking / sensor-fusion 文献中，插值则更加普遍

如果把范围从 XR display runtime 扩展到 tracking/state estimation，就更不能把 interpolation 当 novelty。

MIMC-VINS 在处理多个异步 camera/IMU 时，明确采用 **high-order on-manifold state interpolation**，在各 camera 的异步 imaging time 上获得状态，而无需为每个测量时刻额外建立完整 pose state。([IEEE Xplore][9])

连续时间 VIO/SLAM 进一步把整条 pose trajectory 表示成 spline，使任意 timestamp 都可以查询 pose；continuous-time fixed-lag smoothing 也正是为了不同时间、不同频率的异步传感器而设计。([arXiv][10])

甚至专门针对 out-of-sequence measurement 的 Augmented Fixed-Lag Smoother，也会通过相邻两个 nodes 生成延迟 measurement 对应时刻的状态，再对历史窗口进行更新。([KAIST][11])

但是这里要特别注意一个术语：

### 我仍然不建议把 EgoAnchor 叫做 fixed-lag smoothing

Fixed-lag smoother 通常意味着：

> 当前时刻为 (t)，持续利用新到达的 measurements **重新估计过去 (t-L) 附近的状态**。

也就是说“后来信息改善过去估计”。

而 EgoAnchor 目前是：

> KF 先生成已经接纳的 trajectory nodes；render runtime 再选择过去的 (t_q)，在两个现有 trajectory nodes 之间读取/interpolate。

你们**没有因为选择 (t_q) 而重新优化过去状态**。

因此：

* `fixed-lag smoothing`：不准确；
* `historical trajectory sampling`：准确但太泛；
* `delayed interpolation`：准确；
* **`adaptive-lag trajectory interpolation`**：我认为最适合论文；
* **`buffered historical interpolation`**：也很安全。

# 8. 连“动态物体 6DoF 轨迹 + anchor poses + interpolation”也已经有人做

还有一个非常值得防 reviewer 的先例，虽然不属于 XR。

2024 年的 *Cooperative Image Orientation with Dynamic Objects* 直接把动态物体表示成一系列 **6DoF anchor poses**，并在相邻 anchor poses 之间进行 interpolation，从而获得任意时刻的 object pose。([Springer][12])

所以从数学层面：

> dynamic object + discrete 6DoF poses + interpolation → continuous trajectory

当然也不是新的。

区别仍然在 application/system semantics：这个工作是 photogrammetric bundle adjustment 中对动态对象轨迹进行建模，而不是实时 PMR object anchoring。

# 9. 所以 EgoAnchor 的学术定位应该怎么变？

经过这轮调研，我会把你们的 novelty 边界划得更精确：

**不要 claim：**

> We introduce interpolation to convert low-rate poses into per-frame anchors.

这个肯定不安全。

也不要 claim：

> Existing XR systems primarily rely on prediction, whereas EgoAnchor introduces historical interpolation.

因为 OpenXR 和 Harmonize 已经直接反例。([Khronos Registry][1])

比较安全、而且实际上更有价值的 claim 是：

> Existing XR and tracking systems use prediction, historical pose interpolation, buffering, and late-stage reprojection to reconcile sensing and rendering timelines. EgoAnchor builds on this broader temporal-design space but addresses a different runtime problem: asynchronous visual object observations are associated with past image-capture times rather than render times. It therefore first restores each observation's capture-time world semantics and controls observation reliability, then uses an adaptive lag to query and interpolate the accepted object trajectory without extrapolating unobserved motion.

这里 interpolation 明确是**已有 mechanism**，你们的贡献变成：

[
\boxed{
\text{capture-time semantics}
+
\text{reliability-controlled object trajectory}
+
\text{adaptive lag selection}
+
\text{interpolated per-render-frame anchor}
}
]

而真正有研究意义的是：

[
\boxed{
\text{How should an MR runtime consume delayed,
irregular, uncertain object observations?}
}
]

我认为这比把贡献包装成某个 interpolation algorithm 更符合 **IEEE VR systems paper** 的审稿逻辑。

## 10. 对你们 2.3 Related Work，我现在建议重新分类

标题我甚至建议从：

**“XR 时延补偿与时间一致性”**

改成更准确的：

**“XR Temporal Alignment and Latency Handling”**
中文可写 **“XR 时延处理与时间对齐”**。

逻辑分三段即可：

第一段讲 **prediction / extrapolation**：Azuma → modern predictive tracking。([Ronald Azuma][4])

第二段讲 **reprojection + buffering/interpolation**：post-rendering warping；OpenXR historical pose interpolation；networked XR entity interpolation；MR delay-alignment buffer。([数字对象标识符][7])

第三段再指出你们的 gap：

这些机制分别面向 head/view tracking、networked virtual states 或多流显示同步；对于**外部视觉模型异步返回的真实物体 6DoF observation**，问题还包含 capture-time camera/world semantics、observation reliability、irregular arrival 和失效/reacquisition。EgoAnchor 的贡献不是发明 interpolation，而是把这些因素统一成 object-anchoring runtime。

### 最终结论

所以，对你刚才最核心的问题：

**“学术界没有我们的这种插值吗？”**

答案应该是：

**有相当接近的，而且必须引用。**

尤其是：

**OpenXR historical interpolated poses** 和 **Harmonize entity interpolation**，前者在 runtime semantics 上接近，后者在“故意显示过去 + 两个已知状态间 position/orientation interpolation”的设计思想上非常接近。([Khronos Registry][1])

但目前我没有找到一个 prior 同时覆盖你们的 **异步 zero-shot physical-object observation + capture-time world correction + reliability gating + adaptive observation-age-based lag + SE(3) delayed interpolation + MR object-anchor validity/reacquisition**。这个结论应写成**“我们检索到的 prior 中尚未统一处理这些问题”**，而不是绝对的 “first”。

如果按现在这个文献版图重新写 2.3，我认为论文的学术严谨性会明显提高，而且不会削弱贡献，反而会让 Experiment 2 中 **prediction vs delayed interpolation 的 lag–fidelity trade-off** 变成一个更有理论依据的设计问题。
