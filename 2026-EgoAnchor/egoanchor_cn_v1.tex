\abstract{
我们提出 EgoAnchor，一套面向 passthrough mixed reality 的真实物体锚定框架，研究的问题不是如何单独提高某一帧图像中的 6DoF pose accuracy，而是如何在头显持续运动、外部感知异步返回、pose 低频且间歇失效的条件下，将 camera-space 6DoF object pose stream 转化为世界坐标中稳定、可恢复、可交互的 real-object anchor。EgoAnchor 由 Unity/Quest 前端与 Python 后端组成：前端采集双目 Passthrough Camera 图像、camera info 与观测帧 camera pose，后端执行 prompt-guided segmentation、双目度量深度估计与 model-based 6DoF register/track/re-register。系统的关键机制是 frame-aligned anchoring：每个返回 pose 都依据 \texttt{frame\_id} 回查观测帧采集时刻的相机世界位姿，而不是使用结果到达时刻的 HMD pose，从而显式解耦外部推理时延与头显运动。围绕这一机制，EgoAnchor 进一步引入 reliability-aware anchor control，根据 pose reliability、frame-history validity、pose innovation、result age 与 runtime status 在 Update、Smooth、Coast/Hold、Frozen/Lost 和 Reacquire 等锚定行为之间切换。本文将以 world-space anchor error、head-motion-induced slip、jitter-lag tradeoff、端到端 latency、遮挡/出视野恢复能力和任务可用性为核心指标，评估 EgoAnchor 将异步 6DoF pose stream 转化为可用 MR object anchor 的系统有效性。}

\keywords{混合现实, 真实物体锚定, 对象中心锚定, 6DoF 姿态跟踪, 帧对齐, 可靠性感知控制, 异步感知}

\section{引言}

透视式混合现实中的对象高亮、维修指导、情境标注和近物交互，都依赖虚拟内容能够稳定附着在真实世界中的具体物体上。对应用而言，真正需要的不是某一帧图像中的 6DoF pose matrix，而是一个能够在头显持续运动、视角变化、短时遮挡、推理延迟和跟踪退化下仍保持世界一致性的真实物体 anchor。换言之，MR 应用最终消费的是 anchor behavior，而不是裸 pose。

现有 XR 平台已经提供 world anchors、spatial anchors、image anchors、reference object tracking、fiducial markers 和部分 object tracking 能力。这些机制适合静态空间附着、预定义参考目标、仪器化场景或受限对象类别。然而，面向用户指定、具备先验 3D 模型、由外部异步感知持续驱动的真实刚体对象时，平台级 anchor 能力并不能直接回答低频、含噪、会丢失的 pose stream 如何转化为稳定可用的 MR object anchor。

另一方面，计算机视觉社区已经在 6DoF object pose estimation and tracking 上取得显著进展，model-based register/track/re-register 范式也逐渐接近可部署状态。但对 passthrough MR 而言，pose estimator 输出的是观测帧采集时刻、相机坐标系下的瞬时物体姿态；MR 应用需要的却是世界坐标中、面向渲染和交互的稳定锚定结果。两者之间隔着时间对齐、坐标语义、传输策略、更新控制和恢复生命周期等系统问题。

这一断层在外部感知架构下尤为明显。为了获得更强的对象级感知能力，系统通常将重计算 pipeline 放在 PC/GPU 后端执行；但图像采集、网络传输、模型推理、pose 回传和 Unity 应用更新因此发生时序解耦。即使 camera-space pose 本身准确，如果系统在 pose 到达时使用当前 HMD pose 完成世界坐标变换，而不是使用该观测帧采集时刻的 camera pose，最终 anchor 也会在快速头动下出现可见错位。进一步地，遮挡、出视野、mask/depth 退化和 pose jump 会使“每个 pose 都立即更新 anchor”的策略产生明显不稳定。

本文将该问题概括为 \textbf{pose-to-anchor}：如何把异步返回、低频、带噪、会间歇缺失的 6DoF object pose observations 转化为世界一致、稳定、可恢复、可交互的 MR real-object anchor。我们提出 EgoAnchor，一套面向 passthrough MR 的 frame-aligned and reliability-aware real-object anchoring framework。EgoAnchor 不把 pose estimator 视为最终输出，而是将其视作不可靠观测，并通过 frame-aligned reprojection、latest-only transport、可靠性评分、anchor update policy 和 lifecycle management 生成应用层 anchor。

EgoAnchor 的核心机制是 \textbf{frame-aligned anchoring}。系统在 Unity 侧为每个发送帧保存 capture-time camera world pose，并在 Python 返回 PoseResult 后按 \texttt{frame\_id} 回查该位姿。相机坐标系中的 object pose 因此被映射到真实观测时刻的世界坐标，而不是映射到结果回包时刻的头显坐标。围绕这一机制，本文进一步设计 \textbf{reliability-aware anchor control}：根据感知可靠性、frame history 命中、pose innovation、result age 和 runtime health，在 Update、Smooth、Coast/Hold、Frozen/Lost 与 Reacquire 等行为之间切换，避免错误更新比短时保持造成更严重的 MR 锚定失真。

本文的贡献如下：
\begin{enumerate}
  \item 提出 passthrough MR 中的 \textbf{pose-to-anchor 问题表述}，说明 camera-space 6DoF pose accuracy 本身不足以保证真实物体在 MR 中稳定、世界一致、可恢复地锚定。
  \item 提出 \textbf{frame-aligned and reliability-aware dynamic anchoring framework}，将每个异步返回的 object pose 通过 capture-time camera pose 映射到世界坐标，并根据观测可靠性控制 anchor 更新、保持与重获取。
  \item 实现 \textbf{EgoAnchor} 端到端系统，打通 Quest/Unity 头戴双目透视采集、Python 外部对象级感知、ZMQ Protobuf 数据面、NATS Protobuf pose/command 消息面与 Unity world-anchor runtime。
  \item 建立一套 \textbf{anchor-centric evaluation}，从 world-space anchor error、head-motion-induced slip、jitter-lag tradeoff、latency、recovery 和任务可用性角度评估真实物体锚定，而不是只报告逐帧 pose accuracy。
\end{enumerate}

\section{问题定义与设计目标}

\subsection{Pose-to-Anchor 问题}
本文研究的输入不是完整世界坐标 anchor，而是异步外部感知返回的 camera-space pose observation。给定观测帧采集时刻 \(t_i\) 的物体相机坐标位姿 \({}^{C}\mathbf{T}_{O}(t_i)\)，以及同一时刻相机在 Unity/world 坐标中的位姿 \({}^{W}\mathbf{T}_{C}(t_i)\)，EgoAnchor 需要生成应用层可消费的世界坐标物体 anchor：
\[
{}^{W}\mathbf{T}_{O}(t_i) =
{}^{W}\mathbf{T}_{C}(t_i)\cdot{}^{C}\mathbf{T}_{O}(t_i).
\]
错误但常见的替代做法是使用结果返回时刻 \(t_r\) 的相机世界位姿：
\[
{}^{W}\hat{\mathbf{T}}_{O} =
{}^{W}\mathbf{T}_{C}(t_r)\cdot{}^{C}\mathbf{T}_{O}(t_i).
\]
当头显在 \(t_i\) 与 \(t_r\) 之间发生运动时，该做法会把正确的 camera-space pose 映射到错误的世界坐标位置。

\subsection{系统假设与边界}
EgoAnchor 当前聚焦用户指定、具备先验 3D 模型的真实刚体对象。系统假设 Quest/Unity 侧可获得双目 passthrough 图像、camera info 和每个发送帧的 camera world pose；Python 后端负责对象级感知并返回 camera-space pose observation；Unity 侧拥有 world anchor 的最终解释、过滤和应用权。

本文不试图解决所有动态物体长期持久化问题，也不把平台 spatial anchor 或 6DoF pose estimator 作为直接替代对象。本文关心的是：当外部 pose stream 低频、延迟、含噪、会间歇失效时，MR runtime 应如何把它变成可用的 real-object anchor。

\subsection{设计目标}
EgoAnchor 围绕四个目标设计：
\begin{enumerate}
  \item \textbf{世界一致性：} anchor 应对应观测帧采集时刻的世界位置，而不是 pose 回包时刻的近似位置。
  \item \textbf{稳定性：} 系统应抑制 jitter、pose jump 和因错误更新导致的可见错位，同时明确报告稳定性与响应延迟之间的 tradeoff。
  \item \textbf{可恢复性：} 遮挡、出视野、跟踪退化或用户 reset/reacquire 后，系统应能重新建立可靠 anchor。
  \item \textbf{可诊断性：} 系统应暴露 frame id、timestamp、stage、depth/mask quality、reliability flags、command state 和 anchor state，以支撑实验与复现。
\end{enumerate}

\section{EgoAnchor 方法}

\subsection{方法概览}
EgoAnchor 将 pose estimator 的输出视为不可靠观测，而不是最终应用结果。方法由五个层次组成：
\begin{enumerate}
  \item 通过 Quest stereo/camera info 生成对象级 camera-space pose observation；
  \item 通过 frame id 和 capture-time camera pose history 完成 frame-aligned world mapping；
  \item 使用 latest-only transport 避免 stale frames 和过期 pose 污染实时 anchor；
  \item 估计 pose reliability，并基于 pose innovation、result age 和 runtime status 进行更新门控；
  \item 在 Unity 侧维护 anchor lifecycle，输出 raw、baseline-stable 与 reliability-aware stable anchor。
\end{enumerate}

\subsection{对象中心感知管线}
Python 后端从 Quest 双目输入中生成 camera-space pose observation。该管线包括：
\begin{enumerate}
  \item camera info 到算法处理分辨率的 intrinsics remapping；
  \item prompt-guided segmentation，用于确定当前要锚定的目标对象；
  \item stereo depth estimation，用于提供 metric geometry；
  \item model-based register/track/re-register，用于输出 \({}^{C}\mathbf{T}_{O}\)；
  \item mask/depth/track diagnostics，用于后续可靠性评分。
\end{enumerate}
本节需要强调：这些模块的价值不在于单独成为论文创新，而在于它们共同提供 MR anchor runtime 需要的语义可指向性、度量几何性、可恢复 pose observation 和诊断信号。

\subsection{帧对齐的世界坐标映射}
Unity 在发送每个 stereo frame 时，将该 \texttt{frame\_id} 对应的 capture-time left/right/center camera world pose 写入 \texttt{FramePoseHistory}。Python 返回 \texttt{PoseResult} 后，Unity \texttt{CameraPoseFrameAligner} 按同一 \texttt{frame\_id} 回查采集时刻 camera pose，并将 OpenCV camera coordinate 中的 object pose 转为 Unity camera-local pose，再组合成 world anchor pose。

本节应明确比较：
\begin{itemize}
  \item \textbf{Frame-aligned mapping：} 使用 \(t_i\) 时刻 camera pose，目标是 world consistency；
  \item \textbf{Arrival-time mapping：} 使用 \(t_r\) 时刻 camera pose，在头动和外部推理延迟下会产生 anchor slip。
\end{itemize}

\subsection{Latest-only 异步传输}
EgoAnchor v3 采用双平面通信：
\begin{itemize}
  \item 高频 Quest stereo/camera info 走 ZMQ Protobuf data plane；
  \item pose/status/heartbeat/command 走 NATS Protobuf message/command plane。
\end{itemize}
ZMQ 数据面使用 topic-level latest-drain，避免处理过期帧；NATS 消息面负责小型 pose result、状态事件、心跳和 request/reply command。该设计的论文论点是：实时 MR anchor 更关心最新一致状态，而不是完整消费所有过期观测。

\subsection{可靠性感知的 Anchor 控制}
Reliability-aware anchor controller 是目标论文的关键方法层。它的输入包括：
\begin{itemize}
  \item Python 侧 reliability score 和 reliability flags；
  \item frame history 是否命中；
  \item pose innovation，即当前观测与上一稳定 anchor/预测状态之间的平移和旋转差异；
  \item result age 和 end-to-end latency；
  \item runtime phase、track/re-register 状态、heartbeat 与 command 状态。
\end{itemize}

Controller 输出以下 anchor behavior：
\begin{itemize}
  \item \textbf{Update：} 高可靠、低 innovation 时直接更新；
  \item \textbf{Smooth：} 中等可靠或轻微抖动时进入平滑更新；
  \item \textbf{Coast/Hold：} 短时间无 pose 或低可靠 pose 时保持或短时预测；
  \item \textbf{Frozen/Lost：} 连续低可靠、frame miss 或 heartbeat 异常时停止信任新 pose；
  \item \textbf{Reacquire：} reset/reacquire command 或目标重新出现后重新注册 anchor。
\end{itemize}

核心原则是：在 MR 中，错误更新通常比短时保持更糟。论文需要通过消融实验展示 always update、简单 smoothing、Kalman baseline 与 reliability-aware controller 的差异。

\subsection{命令、状态与生命周期}
NATS request/reply command 包括 reset、reacquire 和 control。command handler 只负责 parse、validate、dedup、enqueue 和 ack；pipeline/GPU 状态由 Python \texttt{TrackingRuntime} 单一 owner 顺序执行。ack 只表示命令已接受或拒绝，不表示重获取已成功。执行结果通过 \texttt{AnchorStatusEvent}、\texttt{ServerHeartbeat} 和后续 \texttt{PoseResult} 反映。Unity anchor lifecycle 应与 Python server state 分离，避免网络层、感知层和 Transform 应用混在一起。

\section{实现}

\subsection{硬件与软件环境}
本节记录 Quest 型号、PC GPU、网络部署、Unity 版本、Python 版本、CUDA/TensorRT/PyTorch 版本和关键模型配置。最终投稿中该节应足够复现，但不展开成安装手册。

\subsection{Unity/Quest 前端}
Unity/Quest 端负责采集 Passthrough Camera stereo frame、camera info 和 capture-time camera pose。关键组件包括 \texttt{StereoFrameSource}、\texttt{CameraInfoSource}、\texttt{FramePoseHistory}、\texttt{QuestStreamPublisher} 和 \texttt{ZmqTopicPublisher}。每次成功编码 stereo frame 时，系统必须以同一事务写入 frame pose history，保证后续 pose-to-anchor mapping 可以按 \texttt{frame\_id} 对齐。

\subsection{Python v3 Runtime}
Python v3 端由 \texttt{TrackingRuntime} 单一拥有 perception pipeline 和 GPU 状态。它从 ZMQ data plane 接收 latest Quest input，运行 YOLOE-26、Fast-FoundationStereo、FoundationPose/Cutie 等 wrapper，生成 camera-space \texttt{PoseObservation}，再通过 \texttt{PoseResultFactory} 发布 Protobuf \texttt{PoseResult}。reset/reacquire/control command 进入 \texttt{CommandQueue}，由 runtime 在 frame 边界顺序执行。

\subsection{协议与通信}
共享协议由 \texttt{EgoAnchor\_Protocol/subjects.v1.json} 和 \texttt{protocol/v1/*.proto} 定义。v3 主线使用：
\begin{itemize}
  \item ZMQ Protobuf data plane：\texttt{egoanchor.v1.quest.stereo}、\texttt{egoanchor.v1.quest.camera\_info}；
  \item NATS Protobuf message plane：\texttt{egoanchor.v1.pose.result}、\texttt{egoanchor.v1.anchor.status}、\texttt{egoanchor.v1.server.heartbeat}；
  \item NATS Protobuf command plane：reset、reacquire、control request/reply。
\end{itemize}
本节必须避免旧 v1 的 ZMQ + MessagePack 表述，除非放在历史实现对比中。

\subsection{Unity Anchor Runtime}
Unity anchor runtime 由 \texttt{PoseResultReceiver}、\texttt{PoseToAnchorRuntime}、\texttt{CameraPoseFrameAligner}、\texttt{AnchorPoseProcessor}、low-pass/Kalman baseline processor 和后续 reliability-aware policy controller 组成。runtime 保留 raw world pose 和 stable world pose，便于论文中进行 raw、low-pass、Kalman 和 full controller 的 ablation。

\subsection{诊断、日志与复现支持}
为支撑论文实验，系统需要记录 frame id、timestamps、network receive/publish time、pose phase、det count、depth valid ratio、depth-in-mask、mask area ratio、reliability score、reliability flags、frame history hit/miss、anchor state、processor output 和 command state。最终实验应能从日志重放并计算 anchor error、jitter、slip、latency percentiles 和 recovery time。

\section{评估设计}

\subsection{研究问题}
本文围绕四个研究问题组织实验：
\begin{itemize}
  \item \textbf{RQ1：} frame-aligned mapping 是否能在头显运动和外部推理延迟下提升 world-space anchoring？
  \item \textbf{RQ2：} low-pass、Kalman 和 reliability-aware update policy 如何影响 anchor stability、lag 和错误跳变？
  \item \textbf{RQ3：} EgoAnchor 在遮挡、出视野、跟踪退化和 reacquire 条件下的恢复能力如何？
  \item \textbf{RQ4：} 更稳定、可恢复的 anchor 是否改善真实物体标注/确认任务中的客观表现或主观稳定感？
\end{itemize}

\subsection{实验条件与 Baselines}
技术实验至少包含静态观察、自然头动、快速 yaw/translation、部分遮挡、出视野后返回和光照/材质变化。主要 baselines 包括：
\begin{enumerate}
  \item arrival-time mapping；
  \item frame-aligned raw；
  \item frame-aligned + low-pass；
  \item frame-aligned + Kalman；
  \item frame-aligned + reliability-aware controller；
  \item no recovery / always update。
\end{enumerate}

\subsection{Ground Truth 与数据采集}
最强方案是使用外部 motion capture 或 tracked rigid body 获得 object 与 HMD/world 对齐。若条件受限，可以使用只用于评估、不用于 EgoAnchor runtime 的隐藏/临时 fiducial 或人工测量静态物体 pose。仅有 overlay 视频不足以支撑论文核心主张，但可作为 supplementary video 的直观材料。

\subsection{评价指标}
主要指标包括：
\begin{itemize}
  \item \textbf{World-space anchor error：} estimated world anchor 与 ground truth object pose 的差异；
  \item \textbf{Head-motion-induced slip：} 静止物体在头动时的 apparent overlay displacement；
  \item \textbf{World-space jitter：} 静止条件下 stable anchor pose 的 temporal dispersion；
  \item \textbf{Lag：} 真实变化或有效 pose 更新到 stable anchor 响应之间的延迟；
  \item \textbf{End-to-end latency：} capture 到 Unity apply 的时延及分模块 breakdown；
  \item \textbf{Recovery success/time：} 遮挡或出视野后恢复到 accepted stable anchor 的比例与时间；
  \item \textbf{Jump rejection：} controller 拒绝的大幅错误 pose jump 数量和幅度；
  \item \textbf{Task usability：} 可选任务完成时间、成功率、主观稳定性和信任感评分。
\end{itemize}

\subsection{任务实验}
如果伦理审批和时间允许，设计轻量 within-subject study。参与者在真实物体上对齐或确认虚拟标签、轮廓或操作提示，并在自然头动、遮挡和重新观察条件下完成任务。条件对比可设为 baseline、frame-aligned raw/stable 和 EgoAnchor full。若无法开展合规人类实验，应使用 recorded trace benchmark 代替，不做用户体验强主张。

\section{实验结果}

\subsection{Frame Alignment 对世界一致性的影响}
本节报告 arrival-time mapping 与 frame-aligned mapping 在静态观察、自然头动和快速头动下的 anchor error 与 head-motion-induced slip。目标论证：即使 camera-space pose 相同，错误的时间坐标组合也会造成 MR world anchor 错位。

\subsection{稳定性、响应延迟与可靠性感知控制}
本节比较 frame-aligned raw、low-pass、Kalman 和 reliability-aware controller 的 jitter、lag、jump rejection 和 stable anchor error。重点不是简单追求最平滑，而是展示稳定性与响应性之间的 tradeoff，以及 reliability gate 如何避免坏 pose 对 anchor 的破坏。

\subsection{遮挡、出视野与重获取}
本节报告部分遮挡、完全出视野、重新观察和主动 reacquire 条件下的 recovery success rate、recovery time 和 failure taxonomy。结果应展示 always update / no recovery 为什么会失败，以及 lifecycle controller 如何在 Hold/Coast/Frozen/Lost/Reacquire 之间保持可解释行为。

\subsection{端到端时延与系统开销}
本节给出 capture、JPEG encode、ZMQ transport、Python perception、NATS publish、Unity receive/apply 等分模块 latency breakdown，并报告 P50/P90/P95。讨论 latest-only strategy 如何减少 stale result 对 anchor 的影响。

\subsection{任务可用性}
若开展任务实验，本节报告任务完成时间、成功率、错误率、主观稳定性和信任感评分。若只做 trace benchmark，则本节改为 recorded-task evaluation，避免写成人类用户研究。

\section{讨论}

\subsection{为什么 Pose Accuracy 不能等价于 Anchor Quality}
本节回到核心论点：camera-space pose accuracy、world-space anchor error、perceived stability 和 task usability 是不同层级的指标。MR real-object anchoring 的失败可能来自 pose estimator，也可能来自错误时间坐标映射、过期帧、滤波滞后、错误更新或恢复策略不当。

\subsection{EgoAnchor 对 XR 系统设计的启示}
总结本文对后续 XR object anchoring 系统的设计原则：外部 pose stream 应被视为不可靠传感器；frame id 和 capture-time camera pose 是跨进程感知的关键 contract；anchor runtime 应显式管理 raw/stable/lost/reacquire 状态；实验应报告 anchor-centric metrics。

\subsection{局限性}
本文系统目前假设已知刚体对象和可用 3D 模型；外部 GPU inference 增加部署复杂度；物体在视野外移动时，简单 hold 策略可能失效；反光、小物体、纹理贫乏、分割失败和 stereo depth 退化仍会导致 tracking/re-register 失败；多物体和长期持久化不是当前主线。

\subsection{未来工作}
未来方向包括多物体 real-object anchoring、头显端轻量部署、学习式 reliability model、跨场景长期持久化、与平台 spatial anchors 融合，以及更大规模任务/用户研究。

\section{结论}
本文围绕 passthrough MR 中的 pose-to-anchor 问题，提出 EgoAnchor 作为 frame-aligned and reliability-aware real-object anchoring framework。论文的核心结论应落在：可用的 MR object anchor 不由单帧 6DoF pose accuracy 自动保证，而需要 capture-time frame alignment、latest-only asynchronous transport、reliability-aware update control 和 anchor-centric evaluation 共同支撑。最终英文稿应基于实验结果明确量化这些机制对 world consistency、stability、latency 和 recovery 的影响。
