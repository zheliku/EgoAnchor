**判断**

可行，而且我认为这是你现在最应该走的方向。

关键不是“把 baseline 也做成模块”这句话本身，而是要把层级说对。`CV / Kalman / OneEuro` 是 **运动模型 baseline** ，`blend / interp / raw` 是 **时间重建 baseline** ，而 `EgoAnchor` 不应该再被塞成和它们同层的“另一个滤波器”。更合理的说法是：

* EgoAnchor 是这个框架上的 **anchor control / anchoring policy**
* 创新点不是谁滤得更平，而是“如何把异步、含噪 pose stream 变成静态更稳、运动可跟、失效可控的 anchor”

**核心结论**

你现在不满意 `blend`、满意 `interp`，这很正常。因为它们优化的是两类不同目标：

* `blend` 优化的是低延迟连续性，天然更容易把小噪声也表现成“微微在动”
* `interp` 优化的是延迟换平滑，所以更容易“看起来稳”

但你真正想要的第三个目标是： **物体静止时尽量像钉住一样不动；物体开始运动时再平滑地释放出来** 。这不是单纯调 `blend` 或 `interp` 参数能彻底解决的，它需要一个 **状态感知的锚定控制层** 。

所以我建议论文和代码都改成这个叙事：

* 共享底座：frame-aligned pose-to-anchor framework
* baseline：`raw / blend / interp` 与 `CV / Kalman / OneEuro` 的组合
* EgoAnchor：在同样底座上增加 **score-aware static anchoring controller**

这也和你论文提纲里“Static Lock / Bounded Prediction / Hold / Reacquire”高度一致，但当前提纲把主角写成了 “reliability-gated One Euro”，这个表述已经偏窄了，[egoanchor_cn_outline.tex (line 36)](/p:/VSCode-Project/EgoAnchor/2026-EgoAnchor/egoanchor_cn_outline.tex:36)。如果你最后最满意的是 `interp + static anchoring`，那论文标题、摘要、RQ2 的 framing 都应该尽快从“某个 One Euro 变体”改成“state-aware anchoring method”。

**推荐落法**

我建议你选这个方案，最稳，也最符合你现在的真实结果：

* 方案 A，推荐：`interp` 作为 backbone，EgoAnchor 作为其上的静态锚定控制层
* 方案 B：`blend` 作为 backbone，再加更强的 gate；不推荐，因为它和你的主观目标冲突
* 方案 C：`interp/blend` 双路径切换；潜力大，但复杂度、解释成本和调参成本都高

如果按方案 A 落，EgoAnchor 的方法就不是“一个新滤波器”，而是一套 mode-based controller：

* `MovingTrack`：正常输出 `interp` 的平滑轨迹
* `StaticLock`：静止时锁住 anchor，抑制毫米级和小角度抖动
* `FrozenUncertain`：低分或坏跳变时 hold 上一个好 anchor
* `Relocalizing / Lost`：恢复与失效管理

**怎么实现**

最重要的一点：**不要只用总分 `ReliabilityScore`。**
Python 端已经把 `final_score = gate × quality × confidence` 分解好了，[pose_quality.py (line 180)](/p:/VSCode-Project/EgoAnchor/EgoAnchor_Python/src/egoanchor/reliability/pose_quality.py:180)；proto 里也已经有 `score_jump / score_confidence / score_depth / score_reprojection`。但 Unity 当前的 `AnchorObservation` 只拿了总分和 flags，[AnchorObservation.cs (line 36)](/p:/VSCode-Project/EgoAnchor/EgoAnchor_Unity/Assets/Scripts/EgoAnchor/Policy/Contracts/AnchorObservation.cs:36)。这不够。

建议实现顺序：

* 第一步：把 `score_confidence`、`score_jump`、`score_depth`、`score_reprojection` 映射进 Unity observation。总分只适合做总开关，不适合做静态锁判据。
* 第二步：在 host 上实现 `StaticLock` 状态，不要再只停留在 `enableScoreGate` 的 reject/hit。
* 第三步：用**迟滞**做进入/退出，避免抖动切态。
* 第四步：锁定时不是永远死锁，而是“小抖动忽略，大偏差慢慢爬，真运动立刻释放”。

一个实用判据可以从这里起步：

* 进入 `StaticLock`：
  * 连续 `N` 帧 accepted
  * `score_confidence` 高
  * `score_jump` 高
  * 速度和角速度都低于阈值
  * 不是 `REGISTER / RE_REGISTER` 新切换帧
* `StaticLock` 内部：
  * 若新观测相对 lock pose 在平移/旋转 deadband 内，完全忽略
  * 若连续多帧都朝同一方向有小偏差，用很小 gain 慢慢把 lock pose 往新位置 creep
* 退出 `StaticLock`：
  * 连续几帧速度升高
  * 或相对 lock pose 超过 unlock 阈值
  * 或 `score_confidence / score_jump` 明显下降
  * 或 relocalization / stale / lost

这套逻辑的好处是：

* 静止时，你的 anchor 是“行为上静止”，不是“统计上更平滑”
* 运动时，它不会一直粘死，因为 unlock 是按真实运动证据释放的
* 低质量观测时，错误更新会被压住，符合 MR anchor 的真实需求

**实验怎么讲**

实验上不要只做“`blend` vs `interp` vs EgoAnchor”这种单层比较，太容易混淆。更稳的组织是：

* RQ1：`arrival-time` vs `frame-aligned`
* RQ2：固定框架下比较 temporal baselines：`raw / blend / interp`，再配 `CV / Kalman / OneEuro`
* RQ3：在最佳 backbone 上做 EgoAnchor 消融：`gate only`、`static lock only`、`full method`

重点指标要加两类，不然你的创新点显不出来：

* 静态指标：静止段 jitter RMS、false unlock rate、static-locked ratio
* 动态指标：motion onset lag、轨迹跟随误差、recovery time

一句话总结：
**baseline 完全可以纳入统一框架，但 EgoAnchor 不该被降格成另一个 baseline filter；它应该被定义成建立在 baseline temporal backbones 之上的 score-aware anchoring controller。** 你现在最值得做的，不是继续磨 `blend`，而是把“静态锁定 + 不确定时 hold + 运动时释放”这层真正做出来。
