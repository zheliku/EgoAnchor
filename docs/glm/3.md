# Unity Anchor 流畅度问题诊断与修复方案

## 一、根因诊断（已用实测数据 + 代码双重确认）

### 核心结论：外推窗口被 clamp 杀死，导致所有方法退化成"阶梯式 ZOH"

 **实测铁证** （`20260614_130324_controller_right_unity_output.jsonl`，逐渲染帧采样，`render_unity_frame` 连续）：

* frame 1501-1506（连续 6 个渲染帧，约 120ms）中，**kalman 的 stable_pos 完全相同** `[-0.0285463,-0.2733265,0.3690542]` ×6，oneeuro、lowpass 同样每帧相同。
* frame 1496→1497 是新 Python pose 到达瞬间（`source_frame_id` 635→640），但 kalman 输出 **那一帧没动** ，到 1497→1498 才阶跃。
* 所有方法的 `predict_ahead_ms` 顶死在各自 clamp 上限：ego=160、kalman=180、oneeuro=120、lowpass=180。
* 实测 capture-to-render 延迟：render_mono_ms(35377) − source_capture_mono_ms(35141) =  **236ms** ，普遍在 180-400ms。

 **根因链** （`KalmanEstimatorModule.cs:111`、`LowPassEstimatorModule.cs:99`、`OneEuroEstimatorModule.cs:100`、`EgoAnchorEstimatorModule.cs:153`）：

![](./material-icons/document.svg)text

```
ahead = Mathf.Clamp(renderTime - lastTimeSeconds, 0, maxPredictAheadSeconds)                                                     ↑ 0.12~0.18s真实延迟 236ms > 上限 180ms → ahead 恒被 clamp 到 180ms→ 每帧 position = x.Position + velocity * 0.180 完全相同→ 连续渲染帧输出一字不差 → 阶梯式冻结
```

外推名存实亡：只有下一个 Python pose 到达（`UpdateEstimate` 改变 x.Position/velocity）时输出才阶跃一次。**所有"做了外推"的方法，实际表现等于比 raw_zoh 更糟的阶梯 ZOH。**

### 次要根因：静止锁把微动也冻死

`StaticLockRateLimitOutputModule.cs:214-235`：`motion_state=Static` 时，estimator 输出相对 lockedPose 偏移 < 3cm/3° 就 **直接返回 lockedPose** 。数据中 egoanchor `static_locked=true` 时连续多帧 stable_pos 一字不差。

### 架构层面：当前是"测量推进、渲染只读"的两时钟架构

* `UpdateEstimate`（Python pose 到达，~32Hz）：`PredictStateTo(captureTime)` 推进 Kalman 状态 + Correct。`lastTimeSeconds = captureTime`。
* `PredictAt(renderTime)`（每渲染帧，~50-90Hz）：**只读** `Position + velocity * ahead`，不修改状态，`lastTimeSeconds` 不变。

`ConstVelocityKalman.Predict` 注释明确写着"供 estimator 在测量时钟和渲染时钟上明确驱动"—— **渲染帧推进状态本就是设计意图，只是当前没实现** ，导致渲染帧只能靠被 clamp 的 ahead 算外推。

## 二、修复方案（已确认路线：A 渲染帧步进 Predict + 静止锁放宽死区平滑）

### 核心架构改动：让 estimator 在渲染帧真正推进状态

把每个 estimator 从"测量推进、渲染只读"改为" **渲染帧持续步进 Predict，测量到达时做时间对齐 Correct** "。这样 `PredictAt` 的 ahead 始终≈0，永不触发 clamp，每帧状态不同→每帧输出不同。

### 改动 1：Estimator 基类不变，但各 estimator 的 PredictAt 改为"推进状态后返回当前状态"

 **KalmanEstimatorModule.cs / EgoAnchorEstimatorModule.cs** ：

`PredictAt(renderTime)` 改为：

![](./material-icons/document.svg)text

```
float dt = renderTime - lastTimeSeconds;if (dt > 0) { PredictStateTo(renderTime); }   // 真正推进 Position/Velocity/协方差// 现在 ahead≈0，直接返回当前状态return new AnchorEstimate(CurrentPose(), LinearVelocity, AngularVelocity, renderTime, ..., ahead≈0);
```

关键：`PredictStateTo` 会更新 `lastTimeSeconds = renderTime`，所以下一帧 dt 又是一个小步长（~14ms），状态每帧平滑推进。

 **时间对齐（UpdateEstimate 改造）** ：测量到达时，状态已在渲染帧被推进到 renderTime（≈现在），但测量是 captureTime（更早）。Kalman 不可逆，无法回退。采用**不回退、基于当前状态 Correct + 观测速度补偿延迟**的策略：

* `UpdateEstimate` 不再 `PredictStateTo(captureTime)`；改为对当前（renderTime 时刻）状态做 Correct，但用放大后的测量噪声吸收"状态已比测量新一个延迟"的误差。
* EgoAnchor 的 `BlendObservedVelocity`（观测速度差分）继续负责补偿 capture-to-render 延迟带来的滞后——这正是它已有的机制，配合渲染帧步进会真正生效。

 **OneEuroEstimatorModule.cs / LowPassEstimatorModule.cs** ：

这两个没有显式 Kalman Predict，但状态 = (filteredPose, velocity)。渲染帧步进 = 用 `AnchorMath.Integrate(filteredPose, velocity, dt)` 把 filteredPose 前推 dt 并更新 lastTimeSeconds。即把当前 `PredictAt` 里的外推结果**写回** filteredPose/lastTimeSeconds，使其成为新的"当前状态"，下次再在前推。测量到达时用 One Euro/LowPass 的正常 Update 融合新测量。

### 改动 2：maxPredictAheadSeconds 语义转变

渲染帧步进后 ahead≈0，`maxPredictAheadSeconds` 不再是日常 clamp。它只在"长时间无测量（如 >300ms）且 estimator 停止步进"时作为安全网。各 estimator 可保留或适度放大此值（如 0.25s），不影响日常平滑。

### 改动 3：静止锁放宽 + 死区平滑（StaticLockRateLimitOutputModule.cs）

* 释放阈值放宽：`staticReleaseMeters` 0.030→0.012，`staticReleaseDegrees` 3.0→1.5（静止锁只在真正几乎不动时生效）。
* 死区平滑：`ApplyStaticLock` 不再"直接 return lockedPose 硬冻结"，改为对 lockedPose 做指数趋近（lerp），让输出缓慢吸附而非瞬冻。具体：`return Pose.Lerp(lockedPose, estimatePose, staticLockFollowAlpha)`，`staticLockFollowAlpha` 默认 0.1（每帧靠近 10%），保留 slip 吸收但消除硬冻结的阶梯。

### 改动 4：运动状态判定保持不变

`AnchorPolicyHost.UpdateMotionState` 的 staticSpeedThresholdMps=0.015 / staticAngularSpeedThresholdDps=1.5 不动。渲染帧步进后 estimator 的速度会更稳定（Kalman 协方差随渲染帧收敛），静止判定会更准，配合改动 3 的死区平滑，静止↔运动过渡会自然。

## 三、不动什么（重要边界）

* **不动** Python 侧（~32fps 是底层感知瓶颈，不在本次范围；本次目标是让 Unity 把 32fps 升采样到流畅 50-90fps 显示）。
* **不动** frame-aligned 对齐（capture-time camera pose 回查是项目核心，保持）。
* **不动** Gate / 状态机 / command 路径。
* **不动** baseline 的 label 集合（raw_zoh/lowpass/kalman/oneeuro/egoanchor_*）。
* `raw_zoh` 保持纯 ZOH（它是 baseline 对照，本就该阶梯，不步进）。

## 六、风险与回退

* 渲染帧步进会让 Kalman 协方差随时间增长（processNoise 累积），可能让测量 Correct 权重变化。 Mitigation：保留 processNoise 现值（位置 0.16-0.20、旋转 0.35-0.40），smoke + 真机验证后按需微调；如出现发散，降低 processNoise。
* 死区指数趋近若 staticLockFollowAlpha 过小会在静止时引入轻微滞后。默认 0.1 偏向平滑，可按真机手感调到 0.2-0.3。
* 全部改动集中在 estimator 内部状态推进策略和静止锁阈值，架构边界（Gate/Output/Host/Runtime）不变，回退只需还原这 5 个文件。
