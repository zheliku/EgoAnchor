**关于你说的"markerless 任意物体锚定是巨大贡献"——这里有个致命的定位陷阱,必须纠正:**

"能锚定任意有模型的刚体"这件事本身 **不是你的新贡献** ,那是 FoundationPose 的能力。如果你把卖点写成"我们能 anchor 任意物体",审稿人会说"这是 FoundationPose 做的,你只是接进了 Unity"——这正是架构文档第 3 节反复警告的"不要写成 YOLOE+FFS+FoundationPose 集成"。

你真正的、属于 IEEE VR 的贡献是 **围绕这个不可靠 pose 流的锚定契约** :

* frame-aligned reprojection(用采集时刻而非到达时刻的 camera pose)
* latest-only 传输
* reliability/jump 门控 + 时序控制
* recovery 生命周期
* anchor-centric 评测(不是逐帧 pose accuracy)

也就是说:**"把异步、低频、含噪、会丢失的外部 6DoF pose 流,变成世界一致、可恢复、可用的 MR anchor"这个系统契约是贡献;"能跟踪任意物体"不是。** 这个区别决定了引言怎么写、related work 怎么摆,直接影响录用。

## Q2：Baseline 是否合理 + 低频转高频

你的直觉(低频不可靠流 → 高频可用状态需要信号扩展)非常对,而且这正是最可辩护的 **技术点** 。但你现在把两个独立子问题混在一起了,必须拆开:

**子问题 A — 去噪/平滑(jitter):** 这是 low-pass / One Euro 解决的。
**子问题 B — 升采样 + 延迟补偿(低频→渲染帧率,并预测以补偿 ~250ms 管线延迟):** 这是**预测/外推**解决的,One Euro  **管不了** 。

关键认知:**vanilla One Euro 是滤波器,不是预测器。** 在 5Hz 输入、70Hz 渲染下,纯 OEF 的输出在两个真样本之间是"平滑后保持(ZOH)",必然有阶梯感和滞后。所以"raw+OEF"作为渲染帧输出,本质是 OEF+ZOH。

### 这里有个会被直接拒稿的公平性陷阱

看你现在的代码:processor chain([RunProcessors](vscode-webview://0ing7s3qthfm1egtmcptmcesnb5om9gpk2n7io0qq2pr7figqgvn/EgoAnchor_Unity/Assets/Scripts/EgoAnchor/Runtime/PoseToAnchorRuntime.cs#L439)) **没有 render-time 的 `Advance(now)` 预测** ,只在收到测量时算一次。而你的 policy 路径每渲染帧 `Advance` 做有界前推。

**如果 baseline 不预测、你的方法预测,你在 lag 指标上必赢——但这是因为对手根本没上场,审稿人一眼看穿。** 必须避免。两个正确做法:

1. **让所有滤波 baseline 共享同一个"预测到渲染时刻"的输出契约** ,只换中间的滤波算法 → RQ2 才是 apples-to-apples;然后把"预测开/关"单独做成一条消融轴。
2. 或者明确声明每个 baseline 是 filter+ZOH,且你的方法的"预测"作为独立机制单独消融。

我推荐做法 1。

### 低频转高频的正确术语与文献(你 related work 要用)

* **Zero-order hold (ZOH)** = 保持上一 pose,最 naive 的 baseline。
* **预测/外推** :constant-velocity / constant-acceleration 运动模型、 **alpha-beta(-gamma) filter** 、带运动模型的  **Kalman predict step** (KF 的预测步天然就是升采样+外推,这是教科书做法)、dead reckoning(网络 VR)。
* **VR 专属** : **predictive tracking / late-stage reprojection / time-warp** 。经典文献是  **Azuma & Bishop 1994/1995 的 predictive tracking for AR registration** ——这是把"预测=延迟补偿"接到 VR 文献的最佳锚点,正好满足架构文档要求的"VR 优先引用"。

### 我建议的 baseline 矩阵(注意两个 RQ 用不同 baseline 集)

你列的 4 个全是 **滤波 baseline(RQ2)** 。但 arrival-time mapping 是 **另一条轴(RQ1,frame alignment)** ,别混进来。

RQ2(时序滤波,共享同一 predict-to-render 输出契约):

| Baseline                         | 滤波 | 升采样/预测                          | 角色                             |
| -------------------------------- | ---- | ------------------------------------ | -------------------------------- |
| Raw(frame-aligned)               | 无   | ZOH                                  | jitter floor + 阶梯感基线        |
| Low-pass                         | EMA  | ZOH/线性                             | 简单稳定性                       |
| **Kalman(const-velocity)** | KF   | **predict-to-now**             | 强基线:原理化的"升采样+预测"对手 |
| Vanilla One Euro                 | OEF  | ZOH(或简单速度外推,声明清楚)         | 交互系统常用低通                 |
| **EgoAnchor(ours)**        | OEF  | **有界前推+score/motion 阻尼** | 你的方法                         |

 **Kalman 一定要做成 constant-velocity 的 predict 版本** ,它就是你"原理化低频转高频"的强对手。如果你的 OEF+有界前推连一个会预测的 KF 都赢不了,那 policy 本来就不该当贡献——这正是消融该回答的问题。

### 你的方法该在哪做"特殊优化"——这是真正的技术增量

是的,你的直觉对。最可辩护的技术贡献不是 OEF,而是  **"被约束的预测"(disciplined prediction)** :

* 按实测端到端延迟(你文档量化的 ~156ms 未补偿)做有界前推补偿延迟;
* 但前推量被  **reliability score 和 motion state 阻尼** ——低分/高不确定/低数据率时缩短或关闭外推,避免过冲。

你的 memory([anchor-policy-motion-regression](vscode-webview://0ing7s3qthfm1egtmcptmcesnb5om9gpk2n7io0qq2pr7figqgvn/index.html?id=102229f5-da88-49e5-94e3-9ba50d2f3747&parentId=1&origin=32e0421f-932d-4e36-9ebd-00d3011fa82e&swVersion=5&extensionId=Anthropic.claude-code&platform=electron&vscode-resource-base-authority=vscode-resource.vscode-cdn.net&parentOrigin=vscode-file%3A%2F%2Fvscode-app&purpose=webviewView&session=435a9207-cb1c-4c7d-98be-33a27aae7e1b))已经用数据证明了反面:4.4Hz 下激进外推导致 37° 摆动。所以你的卖点恰恰是"在低数据率下如何**克制地**预测"——这是 MR 特定的、有数据支撑的、非平凡的机制。这比"我们用了 One Euro"强得多。

## Q1：Baseline 要不要加断线重连？

**核心认知:recovery 是和滤波算法正交的一层,不属于滤波器。** 别把它塞进 baseline 滤波器里。

**没有 pose score 能不能检测断线?能。** recovery 触发信号大部分 **不依赖 score** :

* no-pose 超时(N 秒没来 PoseResult)——这才是真实主导信号
* Python 侧 LOST status 事件(track 自己报丢)
* heartbeat / input_ready
* frame history miss

score 不是 recovery 的必要条件,它只是让 recovery  **更聪明** (在彻底丢之前,基于退化提前 reacquire)。

**实验设计上,recovery 是混淆变量。** 如果只给你的方法 recovery、baseline 不给,你比的就不是滤波器了。正确做法(也正是你论文 RQ2/RQ3 的拆法):

* **RQ2(滤波对比)** :所有条件共享同一套 recovery(或都不开),隔离滤波器。
* **RQ3(recovery 单独作为一条轴)** :no-recovery/always-update vs hold/coast/reacquire 生命周期。

 **而 score-gated 的"主动 reacquire"正好成为你方法在 RQ3 的卖点** :对比"你的 score-aware 主动重获取" vs "naive 纯超时重获取"。这是 score 真正赚到贡献的地方。

所以答案:**baseline 滤波器不加 recovery;recovery 做成独立、可单独开关的共享层;score 不是 recovery 必需,但 score-aware proactive reacquire 是你 RQ3 的独立贡献点。**

## 实现方案：模块化架构

你"每个 baseline 做成模块、可从列表选"的直觉对,而且代码已经有一半了([AnchorPoseProcessor](vscode-webview://0ing7s3qthfm1egtmcptmcesnb5om9gpk2n7io0qq2pr7figqgvn/EgoAnchor_Unity/Assets/Scripts/EgoAnchor/Processors/AnchorPoseProcessor.cs) 子类机制)。但现在的问题是 **两条不可比的代码路径** :processor chain(无 Advance/预测)vs policy host(有 Advance)。要做公平对比必须统一。

### 推荐:统一的 `IAnchorStrategy` 接口(plain C#)

让**所有** baseline 和你的方法都实现同一个接口,既有低频测量入口,又有渲染帧输出入口:

```csharp
public interface IAnchorStrategy {
    void AcceptMeasurement(in AnchorObservation obs);   // ~5Hz,低频测量
    AnchorStrategyOutput Advance(double nowSeconds);      // 渲染帧率,输出契约
    void Reset();
    string Name { get; }
}
```

实现(每个一个模块,enum/下拉选):

* `RawStrategy`(ZOH 透传)
* `LowPassStrategy`
* `KalmanStrategy`(const-velocity,predict-to-now)
* `VanillaOneEuroStrategy`
* `EgoAnchorStrategy`(OEF + score gate + 有界前推 + static lock + reacquire 钩子)← 你的方法

`DynamicObjectAnchor` / 运行时用 enum 选 strategy; **recovery 生命周期是独立组件** (task_plan 里的 `AnchorRecoveryController`),可包在任意 strategy 外、单独开关 → 干净的 RQ3 轴。

关键约束(task_plan.md 已经在坚持的):**strategy 全部写成 plain C#、不读 `UnityEngine.Time`,时间由调用方传入。** 这样同一份 strategy 代码能在 Unity 跑、也能在 headless smoke / 离线回放跑——一份实现,两个执行环境,保证论文数字 == 实时系统行为。

### 两层执行(强烈建议)

1. **Unity 实时** :模块化 strategy 选择,用于 demo + 实时验证 + supplementary video(定性)。
2. **离线回放 harness(真正的实验引擎)** :吃 **一份录制 session** (frame-aligned raw pose + score + 时间戳 + GT),对**同一输入**跑全部 strategy,产出 anchor_error / jitter / lag / latency 表。

为什么实验主力要放离线:保证所有滤波器吃 **完全相同的输入** (无 run-to-run 抖动)→ 对比公平、图可复现。你的 plan 里 `replay_one_euro_policy.py` / `replay_policy_eval.py` 已经是这个方向,只是要扩展成"所有 strategy 一起回放对比",而不只回放 One Euro。

### 和 task_plan.md 的关系(我的判断)

[task_plan.md](vscode-webview://0ing7s3qthfm1egtmcptmcesnb5om9gpk2n7io0qq2pr7figqgvn/task_plan.md) 的 One Euro 重构本身 **合理** ,工程严谨(TDD、smoke gate、离线回放验证),但它 **只解决"把我的方法做好"** ,没覆盖"建可比的 baseline 集"。它的盲点正是上面 Q2 的公平性陷阱:重构后你的 policy 会预测,但 [RunProcessors](vscode-webview://0ing7s3qthfm1egtmcptmcesnb5om9gpk2n7io0qq2pr7figqgvn/EgoAnchor_Unity/Assets/Scripts/EgoAnchor/Runtime/PoseToAnchorRuntime.cs#L439) 的 Kalman/lowpass baseline 还是不预测。

所以我建议在 task_plan 之上加一条 **并行任务** :把 `IAnchorStrategy` 抽出来,让现有 [AnchorKalmanPoseProcessor](vscode-webview://0ing7s3qthfm1egtmcptmcesnb5om9gpk2n7io0qq2pr7figqgvn/EgoAnchor_Unity/Assets/Scripts/EgoAnchor/Processors/AnchorKalmanPoseProcessor.cs) 升级成有 `Advance(now)` 预测的 `KalmanStrategy`,你的 PolicyController 收敛成 `EgoAnchorStrategy`。这样 RQ2 才站得住。
