# 计划：用固定 LensOffset 修正 Unity 侧 pose 固定偏移

## 调整后的判断

- 你的判断更符合当前问题特征：如果偏移是稳定固定偏移，第一版不需要每帧调用或缓存 `PassthroughCameraAccess.GetCameraPose()`。
- 当前 Unity 已经通过 `sourceTarget` 按 `frame_id` 缓存发送帧参考姿态；如果 `sourceTarget` 是 Quest/HMD/CenterEye 这类随头显同步的 Transform，那么它已经提供了每帧的 Unity world pose。
- 缺失的是静态外参：Python pose 来自左 Passthrough 相机图像/左相机坐标系，而 `PoseFollow` 当前把 pose 当成 `sourceTarget` 坐标系下的 pose。应先把参考姿态从 `sourceTarget` 变换到左相机光心：`sourceTargetPose * leftCameraAccess.Intrinsics.LensOffset`。
- Meta MRUK 包源码说明：`Intrinsics.LensOffset` 是 camera sensor relative to headset 的静态 pose；`GetCameraPose()` 本质是 `headPoseAtCameraTimestamp * LensOffset`。因此只要我们已有合适的 `sourceTargetPose`，应用固定 `LensOffset` 就足够修正这类固定偏移。
- 每帧 `GetCameraPose()` 的优势主要是时间戳更精确，能改善快速头动时的动态误差；它不是修正固定外参偏移的必要条件。第一版不引入这条路径，避免复杂化和重复缓存。

## 是否需要 `QuestCameraPoseOffset.cs`

- 第一版不新增 `QuestCameraPoseOffset.cs`。
- 直接在 `PoseFollow.cs` 增加一个可选的左相机 LensOffset 修正，比新增脚本更小、更直接，也避免额外事件绑定。
- 原因：`PoseFollow.OnBeforePoseApply` 当前是通知事件，`Pose` 是值类型，监听器不能把修改后的 pose 返回给 `PoseFollow`；如果硬要做“事件模块返回修正 pose”，需要改事件模型或新增接口，反而比在 `PoseFollow` 内部处理更复杂。
- 修正顺序仍满足需求：`FollowTarget()` 内先把局部 pose 通过 `sourceTargetPose * LensOffset` 转成修正后的 world pose；`Update()` 中再将这个已修正的 `rawWorldPose` 交给 `PoseSmoother`。

## 实施方案

1. 修改 `Assets/Scripts/PoseFollow.cs`。
   - 添加 `using Meta.XR;`。
   - 在 `Alignment` 或新增 `Camera Offset` 区域增加字段：
     - `PassthroughCameraAccess sourceCameraAccess`：绑定左侧 PassthroughCameraAccess。
     - `bool applySourceCameraLensOffset = true`：是否使用 `Intrinsics.LensOffset` 修正参考系。
     - `bool logLensOffsetDiagnostics = false`：可选限频诊断日志。
   - 保持 `sourceTarget` 和 `sourceTargetCacheSize` 的现有行为不变。

2. 在 `PoseFollow.FollowTarget(Pose pose, long frameId)` 中应用 LensOffset。
   - 仍然先用 `frameId` 命中 `sourceTargetPoseCache`。
   - 默认 `referencePose = sourceTargetPose`，保持旧行为作为回退。
   - 如果 `applySourceCameraLensOffset=true` 且 `sourceCameraAccess` 有效，则读取：
     - `Pose lensOffset = sourceCameraAccess.Intrinsics.LensOffset`
   - 组合得到左相机世界参考姿态：
     - `referencePosition = sourceTargetPose.position + sourceTargetPose.rotation * lensOffset.position`
     - `referenceRotation = sourceTargetPose.rotation * lensOffset.rotation`
   - 再把 Python/Decoder 输出的相机局部 pose 转到 Unity world：
     - `worldPosition = referencePosition + referenceRotation * localPosition`
     - `worldRotation = referenceRotation * localRotation`
   - 如果 `sourceCameraAccess` 未绑定、未播放或 LensOffset 无效，则继续使用旧的 `sourceTargetPose`，不阻断 pose 应用。

3. `Update()` 顺序保持不变。
   - `rawWorldPose` 此时已经包含 LensOffset 修正。
   - `OnBeforePoseApply(rawWorldPose, frameId, sampleTime)` 触发。
   - `poseSmoother.ApplySmoothing(rawWorldPose, frameId, sampleTime)`。
   - `transform.SetPositionAndRotation(...)`。
   - `OnAfterPoseApply(...)`。

4. Inspector 配置。
   - `PoseFollow.sourceTarget` 继续绑定当前用于同步 Quest/HMD/CenterEye 的参考 Transform。
   - `PoseFollow.sourceCameraAccess` 绑定左侧 `PassthroughCameraAccess`，因为当前算法 pose 参考左目图像/左相机坐标。
   - `QuestStereoEncoder.OnFrameEncoded(frame_id)` 仍只需要绑定 `PoseFollow.HandleFrameEncoded(frame_id)`，不新增第二个每帧缓存绑定。
   - 如果某个场景中 `sourceTarget` 已经是左 Passthrough 相机自身的 pose，则关闭 `applySourceCameraLensOffset`，避免重复应用外参。

## 风险与验证

1. 主要风险：`sourceTarget` 的参考原点必须与 Meta `LensOffset` 的“headset”参考原点一致或足够接近。
   - 如果 `sourceTarget` 是 XR Camera/CenterEye，一般应接近；如果它是显示屏、任意父节点或经过额外偏移的对象，则 LensOffset 可能只修正一部分。
2. 可用 `PcaApiInfoDumper` 的日志辅助验证：
   - 对比 `GetCameraPose()` 与 `sourceTargetPose * Intrinsics.LensOffset` 是否位置/朝向接近。
   - 如果二者接近，说明固定 LensOffset 路径正确。
3. 实机对比：
   - 关闭 `applySourceCameraLensOffset` 记录原偏移。
   - 开启并绑定左相机，观察物体是否整体对齐真实目标。
   - 如果偏移方向明显反了或变大，优先检查是否重复应用了相机外参，或 `sourceTarget` 不是 headset/CenterEye 参考系。
4. 不改网络协议、不改 Python、不改 `QuestCameraInfoMsg`，第一版只在 Unity 位姿应用侧修正参考系。

## 暂不做

- 不新增 `QuestCameraPoseOffset.cs`。
- 不每帧调用或缓存 `GetCameraPose()`。
- 不增加手动调参 offset；如果固定 LensOffset 后仍有小残差，再考虑 debug-only 手动微调。
