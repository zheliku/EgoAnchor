# Unity Pose Reference Drift 分析与修复计划

## 本轮用户澄清

用户强调的核心点是正确的：

- Python 每次传来 pose 时，Unity 应该用该 `frame_id` 对应的发送帧相机/参考姿态计算一次世界 pose。
- 计算出的目标世界 pose 应该成为后续应用目标。
- 后续每帧 `Update()` 不应该再读取当前 `sourceTarget` 或重新把当前 HMD transform 乘进去。
- 如果移动头显后物体仍跟随移动，怀疑是不是每帧又和当前 `sourceTarget` 绑定。

## 已确认结论

### 1. `PoseFollow.Update()` 本身不会每帧读取 `sourceTarget`

文件：`Assets/Scripts/Pose/PoseFollow.cs`

`Update()` 逻辑：

```csharp
Pose processedPose = _rawWorldPose;
foreach (PoseProcessor processor in processors)
{
    processedPose = processor.Process(processedPose, _latestFrameId, sampleTime);
}
transform.SetPositionAndRotation(_processedWorldPose.position, _processedWorldPose.rotation);
```

只读检查结果：

- `Update()` 不访问 `sourceTarget`。
- `Update()` 不访问 `sourceCameraAccess`。
- `Update()` 每帧应用的是已经保存的 `_rawWorldPose` 经 processors 后的 `_processedWorldPose`。
- `PoseSmoother` 和 `PoseKalmanFilter` 也只处理输入 world pose，不访问 `sourceTarget` 或相机 transform。

所以“同一个已经算好的 `_rawWorldPose` 每帧又被当前 `sourceTarget` 绑定”的猜测，在 `PoseFollow.Update()` 代码层面不成立。

### 2. `sourceTarget` 只在两个时刻使用

`sourceTarget` 只在：

1. `HandleFrameEncoded(frameId)`：编码出一个 stereo frame 时，缓存当时的 `sourceTarget.position/rotation`。
2. `FollowTarget(pose, frameId)`：收到 Python pose 时，用缓存的 `sourceTargetPose` 把 camera-local pose 转为 world pose。

因此，如果没有新的 pose 消息进入，移动头显不应该改变该物体的 Transform，除非：

- 物体是某个会动 transform 的子物体；检查 scene 中两个 cube 的 `m_Father` 都是 `{fileID: 0}`，不是 HMD 子物体。
- 有其他脚本每帧修改物体；`Assets/Scripts` 中只有 `PoseFollow.Update()` 调用了 `transform.SetPositionAndRotation`。
- Unity XR/OVR 视觉呈现导致你看到的是相对视角变化，而不是物体世界坐标变化。

### 3. 更可能的真实原因：不是“同一个 pose 每帧绑定 sourceTarget”，而是“每个新 pose 都重新用新的发送帧 sourceTarget 计算”

虽然 `Update()` 不读当前 `sourceTarget`，但只要 Python 持续发送 pose，`FollowTarget()` 就会反复执行。

每次 `FollowTarget()` 都会拿对应 frame 的缓存相机/参考姿态：

```csharp
_sourceTargetPoseCache.TryGetValue(frameId, out Pose sourceTargetPose)
```

也就是：

- frame 100：用 frame 100 发送时 HMD/sourceTarget 姿态算 world pose。
- frame 101：用 frame 101 发送时 HMD/sourceTarget 姿态算 world pose。
- frame 102：用 frame 102 发送时 HMD/sourceTarget 姿态算 world pose。

如果 HMD 移动了，新的 sourceTargetPose 每帧当然会变。

正常情况下，Python 返回的 camera-local pose 也应该随着相机运动产生反向变化，两者相乘后世界 pose 应保持稳定：

```text
world_T_object = world_T_camera(frame_id) * camera_T_object(frame_id)
```

如果物体世界 pose 跟着 HMD 走，说明这个抵消没有发生或发生错了。原因通常是：

- Unity 使用的 `world_T_camera(frame_id)` 不是 Python 图像对应真实相机的 world pose。
- `sourceTarget + LensOffset` 方向/基准错误。
- Python 输出的 `camera_T_object` 在 track 阶段没有正确随相机运动更新，而是近似沿用上一帧/被 2D adjust 锁住。
- frame_id 虽然命中，但编码事件发生在真正采样纹理之前，头动快速时存在 capture pose 与 image 时间偏差。

### 4. Scene 绑定还存在干扰项

`Assets/Scenes/Test-QuestStereoSender.unity` 中有两个对象同时消费同一 pose：

- `Cube`
- `Cube (1)`

两者都是 root 物体，不是 HMD 子物体。但事件绑定重复：

- `QuestStereoEncoder.OnFrameEncoded` 同时绑定两个 `HandleFrameEncoded`。
- `PoseDecoder.OnPoseReceived` 同时绑定两个 `FollowTarget`。

这会导致两个 cube 都被 pose 驱动，可能造成观察混乱。建议实现阶段清理 scene，只保留一个目标对象。

## 如何确认用户的猜想

### 测试 A：断开 pose 接收后移动头显

在 Unity 运行中临时停掉 Python pose 输出或禁用 `PayloadReceiver`：

- 如果 cube 仍然跟着头显移动：说明确实有每帧绑定/父子层级/其他脚本问题。
- 如果 cube 不再更新而保持世界坐标：说明不是 `Update()` 绑定当前 sourceTarget，而是每个新 pose 触发 `FollowTarget()` 后重新计算世界 pose。

根据代码，我预期是第二种。

### 测试 B：在 `PoseFollow` 加诊断字段/日志

实现阶段给 `PoseFollow` 增加可选 debug：

- `debugPoseFollow`
- `debugLogIntervalSec`
- 每次 `FollowTarget()` 输出：
  - `frameId`
  - `sourceTarget.name`
  - `sourceTargetPose.position`
  - `pose.position`（Python local pose）
  - `_rawWorldPose.position`
- 每帧 `Update()` 可选检测：
  - 如果 `_rawWorldPose` 没变但 transform 变了，说明有其他脚本/父子层级。
  - 如果 `_rawWorldPose` 随每个 pose 消息变，说明问题来自 camera-local pose 与 source pose 没抵消。

### 测试 C：缓存首次 world pose 并冻结应用

实现一个临时开关：

```csharp
[SerializeField] private bool freezeAfterFirstPose;
```

收到第一个有效 pose 后不再更新 `_rawWorldPose`。

- 若 freeze 后移动头显物体不动：再次证明不是每帧绑定 `sourceTarget`。
- 若 freeze 后仍跟动：说明物体父级/其他脚本/显示参考有问题。

## 修复方向

### 阶段 1：增加诊断与冻结开关，不改协议

在 `PoseFollow` 中增加：

- `debugPoseFollow`
- `freezeAfterFirstPose`
- 可选 `logPoseEveryNSeconds`

目的：快速区分：

1. `Update()` 每帧绑 sourceTarget。
2. 每个新 pose 重新计算出的 world pose 在漂。
3. 其他脚本/父子层级在改 transform。

### 阶段 2：清理 scene 重复绑定

在 `Test-QuestStereoSender.unity` 中：

- 只保留一个 cube 监听 `QuestStereoEncoder.OnFrameEncoded`。
- 只保留一个 cube 监听 `PoseDecoder.OnPoseReceived`。
- 禁用或删除另一个 `CubeFollow` 监听项。

### 阶段 3：验证 sourceTarget/LensOffset 口径

在同一个 cube 上测试：

- `applySourceCameraLensOffset = true`
- `applySourceCameraLensOffset = false`

若还不够，再实现 lens offset 方向选择：

```csharp
source * lensOffset
source * inverse(lensOffset)
```

### 阶段 4：如 Python track 不随相机运动抵消，回到 Python 侧诊断

如果 Unity debug 显示：

- `sourceTargetPose` 随头动变化。
- `pose.position` 没有相应反向变化。
- `rawWorldPose` 跟着 sourceTarget 变化。

则问题可能在 Python 的 FoundationPose track/depth/mask 输入，使返回的 object-in-camera pose 没正确跟随相机变化。需要检查：

- FFS 深度是否跟随相机正确变化。
- Cutie adjust 是否强行用 2D bbox 中心修正 tx/ty，导致 pose 跟着画面中心/HMD 漂。
- `--cutie_adjust_pose 0` A/B 测试。

## 当前判断

用户的直觉“如果算出 world pose，之后不该每帧绑定 sourceTarget”是对的。

但代码检查显示：

- `PoseFollow.Update()` 不会每帧读取当前 `sourceTarget`。
- 更可能是 Python 持续发送新 pose，每次 `FollowTarget()` 都用新的 frame 对应 `sourceTargetPose` 重新算 world pose。
- 正常这应该抵消头动；若没抵消，说明 `sourceTargetPose` 和 Python pose 不是同一个真实相机/时间/坐标口径，或 Python track 本身没有正确输出随相机变化的 object-in-camera pose。

## 实施计划

1. 在 `PoseFollow` 增加 `freezeAfterFirstPose` 和 `debugPoseFollow` 限频日志。
2. 清理 `Test-QuestStereoSender.unity` 中重复 cube 事件绑定，只保留当前观察对象。
3. 用 freeze 测试确认是否存在每帧绑定 sourceTarget。
4. 用 debug 日志确认每次新 pose 的 `sourceTargetPose`、local pose、world pose 如何变化。
5. A/B 测试 `applySourceCameraLensOffset` 与 `--cutie_adjust_pose 0`。
6. 根据日志结果决定是否增加 lens offset inverse mode 或调整 Python tracking 配置。
